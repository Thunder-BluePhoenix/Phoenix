# capabilities/calendar

Read-only calendar awareness: upcoming meetings, a fresh deploy-freeze snapshot and a `calendar.meeting.starting_soon` event with prep from reviewed prior meetings. Disabled until the owner enables it and turns on at least one provider.

## Behaviour

- Manifest permissions are `network` and `external_api` (both in the protocol permission list); `data_categories` also discloses that calendar account credentials sit in OS secret storage and go only to the provider's own host. The privacy inventory (`GET /api/privacy`) lists a stored `caldav_credential`, `google_credential` or `microsoft_credential` by name only. The only command, `upcoming`, has side effect `read`. No adapter issues a write.
- Providers (Google, Microsoft Graph, CalDAV, macOS) are selected by boolean config. Core builds the adapter for each enabled provider **when the feed is read**, from the capability's own config and secret; nothing is hard-coded and `createCalendarCapability()` needs no arguments. Nothing switched on means the feed is `unconfigured` and nobody is contacted. A network provider without its `<provider>_credential` secret is never queried, and the whole feed is then reported unavailable (`<provider> credential missing`) without advancing `checkedAt`.
  - **CalDAV** (real HTTP transport, `src/caldav.ts`): config `caldav: true`, `caldav_url` (ONE collection, https, or http only to localhost; no credentials, query or fragment in it; validated in the manifest schema and again at read time) and optional `caldav_timezone` (IANA, default UTC, for all-day and floating times). Secret `caldav_credential` is `username:password` (an app password) sent as HTTP Basic **only** to the host in `caldav_url`. One read-only `REPORT` (`calendar-query` with server-side `<expand>`) per read; no other method; `redirect: "error"` so the credential never travels to another host; 15 s deadline over connect and body; answer capped at 2 MiB (by header and while streaming). The `upcoming` result shows `sends_caldav_credential_to` (the host). The 207 multistatus is read with a linear tokenizer (no DTD or entity resolution) and the iCalendar objects by `src/ics.ts`. A non-200 status inside the multistatus, a result without calendar data, an event still carrying `RRULE`/`RDATE` (server did not expand) or an unreadable time fails the whole feed (`caldav ...` fixed phrases). Phoenix never expands a recurrence itself.
  - **Google / Microsoft Graph** (`src/providers.ts`): config `google: true` / `microsoft: true`; secrets `google_credential` (OAuth access token, `calendar.readonly`) and `microsoft_credential` (Graph access token, `Calendars.Read`) sent as `Authorization: Bearer` only to `https://www.googleapis.com` / `https://graph.microsoft.com` (code constants; the `endpoints` option exists for tests and accepts only https or loopback; never a config setting). GET only, redirects refused, 2 MiB cap, 15 s deadline, fixed secret-free error phrases (for example 401: "... rejected the credential (401): check it is valid and not expired"). **Phoenix has no OAuth flow and never refreshes a token**: you obtain the access token yourself, and when it expires (roughly an hour) the feed becomes unavailable until you store a new one. A short-lived token makes this a poor fit for an always-on feed; it is the only honest option without OAuth.
  - **macOS: no reader in this build.** The adapter calls a `calendar-read` helper that expands recurrences, which Calendar's own scripting interface cannot do reliably, and nothing in this repository implements it. `macos: true` without a host-supplied reader (`createCalendarCapability({ adapters: { macos } })`) makes the feed `unavailable` ("macos calendar reader is not available in this build"), never silently empty.
  - `createCalendarCapability({ adapters })` still lets a host (and tests) supply a ready adapter; it wins over the built-in one.
- Recurrences are expanded by the provider (Google `singleEvents`, Graph `calendarView`, CalDAV/macOS expanded objects); the adapters never guess occurrences. Events are normalised by `safeEvent`: a private event keeps no title, attendees or link (Graph `personal` counts as private), private events are reduced to `Busy` with no attendees, link or freeze flag, only https links without credentials survive, and attendees must look like emails.
- `freezeAt` treats a freeze as the half-open window `[start, end)`; only explicitly marked, public, non-cancelled events count. A failed read keeps `error` set and health degraded, so a stale feed is never presented as current.
- Reminders fire once per occurrence id and start time, from five minutes before start until start, never for private or cancelled events. With the `reminderStore` option (Core passes one backed by the settings key `calendar.reminders.sent`) the de-dup keys survive a Core restart: only an opaque SHA-256 digest and the start time are stored, expired after the start, capped at 500, and corrupt stored data is ignored. If the store fails the reminder is still sent once, silently. Without a store, de-duplication is in memory only.
- Prep (`prepareMeeting`, `src/prep.ts`) is pure. It uses only the injected `MeetingPrepQuery`, which Core backs with reviewed meeting items; accepted or edited decisions and open action items only, with no transcripts. `ReviewedItem.closed` is optional; absent means open.

## Evidence

Tests (`test/calendar.test.ts`, `test/feed.test.ts`) use injected fake clients and a runner with hand-written payloads shaped from my reading of each provider's documentation. They cover the four adapters, `safeEvent` sanitisation, `freezeAt` boundaries, the reminder book (including persisted keys) and prep filtering. `test/providers.test.ts` runs the production CalDAV transport, Google and Graph clients against loopback fake servers: config validation, host and URL checks, redirect refusal, size caps (declared and streamed), deadlines for a silent and a dripping server, partial or unexpanded answers, secrets absent from events, errors and snapshots, "unconfigured stays unconfigured", and the same events and reminder as the fake-adapter path. `core/runtime/test/calendar-caldav.test.ts` drives a real `PhoenixRuntime` with `builtinCapabilities`-style wiring through the HTTP API (config, write-only secret, privacy inventory). `core/runtime/test/calendar-reminders-restart.test.ts` restarts a real `PhoenixRuntime` on the same database. All of it is simulated evidence: **no real account, calendar server or token was used.**

## Unmet exit criterion

**Not met: no real calendar has been read.** Nothing here has run against Google, Microsoft Graph, a CalDAV server or macOS Calendar, so real field names, time-zone formats (including Windows zone names from Graph), recurrence/exception shapes, CalDAV XML/ICS parsing and credential/OAuth flows are unverified. The CalDAV transport and iCalendar reader were only run against a fake server written from RFC 4791/5545; real servers' multistatus shapes, expansion behaviour, time zone definitions (`VTIMEZONE` is ignored, only IANA `TZID` names are read) and rate limits are unverified. The macOS reader does not exist. The exit criterion needs verification against at least one real account per provider before it can be claimed.

## Feed integrity (fail closed)

- A feed is complete or it is unavailable. If any configured provider has no credential, throws, is paginated (`nextPageToken`, `@odata.nextLink`), returns more than 500 events, or returns any non-cancelled event that cannot be read (bad id, date or IANA zone), the capability sets `error`, returns no events and does not advance `checkedAt`. Nothing is silently dropped, because a dropped row could be a deploy freeze.
- Freeze holds may be longer than 31 days; ordinary events are still capped at 31 days.
- Offset-less Graph/CalDAV/macOS date-times and all-day Google dates are read as wall-clock time in the event's own time zone, never the host's.
- `upcoming` is cached; `{ "refresh": true }` re-reads providers when the cache is older than 30 seconds or errored. Core's freeze snapshot always asks for that.

## Marking a deploy freeze

- **Google:** the private extended property `phoenix.deployFreeze=true` on the event, or a title starting with `[deploy-freeze]` on an event you organise. Google Calendar has no `categories` field, and invited events' titles are ignored so a stranger's invitation cannot create a hold.
- **Microsoft Graph / CalDAV:** the category `deploy-freeze`. **macOS:** the runner's `deployFreeze` flag.
- Private events never impose a hold.
