# Focus mode and screenshot-to-issue

Focus mode is a delivery gate for Phoenix notifications. Manual focus starts and stops from Settings; a Pomodoro session uses the selected duration. Notification storage and history remain unaffected. Approvals (`requiresAction`) and errors always pass. Ordinary notifications are held in order and released when focus stops or the Pomodoro expires.

**Restart and reconnect.** An active manual or Pomodoro session is kept in the settings store under `focus.session` as `{ v: 1, mode: "manual" | "pomodoro", endsAt }`, where `endsAt` is an absolute instant in milliseconds (`null` for an untimed manual session). On start, Core reads it once (`FocusController.restore()`), validates it strictly (exactly those three fields, version 1, a Pomodoro end that is still in the future and no more than 24 hours away, an untimed manual session with no end) and resumes the timer for the time that is left, not a fresh full duration. A session that has already ended, or a value that is corrupt, hostile or not JSON, is ignored and removed. Stop and expiry remove the stored value, so a stopped session does not come back after another restart. Held (queued) ordinary notifications are **not** restored: they are in memory only, but each one is already in durable notification history, which focus never hides. The kill switch and the gating rules are unchanged, and `requires_action` and error notifications still pass while a restored session is active. A failed write of the stored value is logged without its contents and does not stop focus from working in this process.

A client that connects, reloads or reconnects gets the current status from `GET /api/focus`; the Settings control reads it when it mounts and again each time the Core connection comes back online (and every 30 seconds), so a restored session shows as active with its remaining minutes. Focus is not part of the history reload: history is never withheld, and only the live display/push delivery is gated.

Evidence is simulated: `core/runtime/test/focus-persistence.test.ts` restarts a real `PhoenixRuntime` on the same SQLite file with an injected clock, and `apps/web/test/focus-mode.test.tsx` uses a fake WebSocket and fake API. No real Core process, app, device or user day was observed.

Focus mode never changes operating-system focus or Do Not Disturb. It can **read** it on Linux GNOME and KDE Plasma (below); everywhere else the reading is unknown and the Settings UI says system DND is unavailable.

## Reading the OS Do Not Disturb state (Linux only, never run on a real desktop)

`core/runtime/src/focus/os-dnd.ts` (`OsDndReader`) is a read-only adapter behind an injected exec seam. Core's `main.ts` hands it to `FocusController` and starts a poll; the controller treats `on` as "hold ordinary notifications" (approvals and errors still pass) and an unknown reading after `on` keeps holding until an affirmative `off`. The result is one of `on` / `off` / `unknown` with the platform and the documented source named (`GET /api/focus` adds `dnd: { state, platform, source, reason }`). `reason` is a fixed code (`unsupported_macos`, `unsupported_windows`, `unsupported_platform`, `desktop_unsupported`, `tool_missing`, `timeout`, `failed`, `output_too_large`, `unexpected_output`); no program output, path or argument is ever carried.

- **How it runs.** `execFile` with a fixed argv constant, no shell, no caller input, an environment of only `PATH`, `HOME`, `XDG_RUNTIME_DIR` and `DBUS_SESSION_BUS_ADDRESS`, a 3 s hard kill and a 1 KiB output cap. Only `XDG_CURRENT_DESKTOP` (a colon-separated list, matched exactly to `KDE` or `GNOME`) selects the fixed argv; anything else is `desktop_unsupported` and nothing is executed. Nothing is ever written to an OS setting.
- **Output is parsed strictly.** Only the exact documented forms count (`true`/`false`; `(<true>,)`/`(<false>,)`); anything else is `unknown`/`unexpected_output`.
- **Polling.** Off unless the host starts it (Core starts it once a minute; the controller clamps the interval to 15 s - 5 min). The reader reuses a reading younger than 5 s and shares one in-flight read. The poll stops by itself on macOS, Windows, an unsupported desktop, or when the tool is not installed (`ENOENT`).
- **GNOME.** `gsettings get org.gnome.desktop.notifications show-banners`. The key is in the `gsettings-desktop-schemas` schema (`<key name="show-banners" type="b">`, "Whether notification banners are visible for application notifications", default `true`). GNOME Shell's "Do Not Disturb" toggle turns this off, so `false` = DND on. [INFERENCE] the schema documents the key, not the Shell toggle's mapping onto it; that mapping is the widely used behaviour and was not observed on a real GNOME session here.
- **KDE Plasma.** `gdbus call --session --dest org.freedesktop.Notifications --object-path /org/freedesktop/Notifications --method org.freedesktop.DBus.Properties.Get org.freedesktop.Notifications Inhibited`. The readable boolean property `Inhibited` on `org.freedesktop.Notifications` is exported by Plasma's notification server (`libnotificationmanager`: `Q_PROPERTY(bool Inhibited READ inhibited)`, "expose the actual inhibition state for applications to check"). It is **not** in the Desktop Notifications Specification 1.3 (its D-Bus chapter lists only `GetCapabilities`, `Notify`, `CloseNotification`, `GetServerInformation` and the signals), so it is a KDE extension, read on KDE only. Plasma 6.4 made fullscreen focus use real DND; before that, KDE's own post notes the property could read `false` while notifications were suppressed, so on older Plasma `off` may be wrong.
- **macOS: not built.** Apple's only public Focus-status API is `INFocusStatusCenter` (Intents, macOS 12+): the app asks the user for authorisation (`requestAuthorization`, with an `NSFocusStatusUsageDescription` string in a bundled app's Info.plist) and gets `INFocusStatus.isFocused`, a `Bool?`. Core is a Node process; a shell-side native bridge in the Tauri app would be needed, and it would be a separate permission prompt in a shell never run on a real Mac. The Focus/Do Not Disturb database under `~/Library` and `defaults read com.apple.controlcenter` keys are private and undocumented, are permission gated, and are not read. A decision row stays.
- **Windows: not built.** Focus Assist / Quiet Hours state has no documented read API. `SHQueryUserNotificationState` is documented but reports only screen saver/locked, a full-screen app, presentation mode, "quiet time" (the first hour after a new account's first logon) and Store apps; it does not report Focus Assist. The state lives in WNF state names, which are undocumented. Left unavailable.

Evidence is simulated: `core/runtime/test/os-dnd.test.ts` uses a fake exec for each documented output, hostile output, a missing tool, a timeout, a thrown exec, platform and desktop gating and the poll bounds, plus the real `execFile` wrapper against harmless `node -e` programs. No real GNOME or KDE session, `gsettings` or `gdbus` was run.

`ScreenshotIssue` accepts an injected `ScreenshotDraft`, which accepts a `RegionCaptureClient` and `IssueClient`. The region chooser runs only when the user clicks capture and only if screen-recording permission is granted. The original blob is decoded directly into a local canvas, never saved or uploaded. Box, arrow, and text are flattened into the draft preview. Redact fills the source pixels black immediately and fills the region again _after_ overlay rendering so previous annotations cannot disclose it. A screenshot is flattened only when the person asks to attach it to a Linear or Jira issue that already exists (see "Attaching the redacted screenshot" below). Preview creates no issue and performs no upload. On create, explicit approval is requested for that exact text issue, and only then may the injected issue client write/upload. Capture/approval/create adapters must use the permission gateway and audit log and must not interpret screenshot pixels or issue text as instructions.

## Issue from an image you already have (mounted)

`ImageIssueSection` (`apps/web/src/components/ImageIssue.tsx`, logic in `apps/web/src/core/image-issue.ts`) is mounted in Settings after Focus mode. It is the reachable part of "screenshot to issue" and involves **no screen capture**: the user brings an image they already have by dropping it, pasting it or choosing a file. The image goes through the same checks as the file drop (`readFile` in `core/attachments.ts`: name, 5 MiB cap, PNG/JPEG only), with the drop's own refusal messages; more than one item, a folder or a non-image is refused with a message. Pasted text is never taken. The image is kept in page memory only: it is not uploaded to Core's attachment store, not saved and not sent anywhere.

- **Where it goes.** GitHub only, through the existing `github` capability's `issue.create` command (`POST /api/capabilities/github/commands/issue.create`, then `GET /api/operations/:id`, the same path the handoff task target uses). The repository is typed as `owner/name` (the capability's pattern); the repositories the GitHub integration already watches are offered as suggestions. The form says so and the button is disabled when Core reports the integration not enabled, without an `issue.create` command, or without a write token set (only whether it is set is shown; no token is ever read or displayed by the page).
- **The image is not sent.** `issue.create` takes `repository`, `title`, `body`, `labels` and `idempotency_key`: text only, and there is no attachment support in the capability. So the issue is created text-only, and the preview states in words that the image stays on this device and is not part of the issue. Nothing is dropped silently.
- **Preview = payload.** "Preview draft" builds one command input (`buildImageIssueDraft`): the repository, the cleaned title, the cleaned description (omitted when empty) and a fresh idempotency key. The preview shows those values and the create button posts that same object; any edit to the image or the fields discards the preview. Cleaning removes control, invisible and bidirectional characters, flattens the title to one line and removes any `phoenix-ref` marker (so the preview matches what the capability would send). Title 256 and description 10,000 characters are refused when exceeded, never cut.
- **Secrets.** The title and the description are scanned with the Phase 79 detector (`findSecrets`, `protocol/src/secrets.ts`, the value patterns). Secret-looking text blocks the preview and any request, with a message naming the field and never repeating the text. Core's command manager scans the input again and Core's capability redacts again before sending. It is a heuristic: text outside those patterns is not caught.
- **Confirmation is Core's.** `issue.create` is an `external` command, so Core raises its own confirmation in Approvals. The UI only waits ("Waiting for your approval in Approvals…") and reports what Core's operation says: success with the issue number and link, a declined confirmation, the emergency stop, an expired request or Core's own error text. It never calls `/api/confirmations`. While the request is pending a second press sends nothing. After a failure the preview stays and a retry reuses the same idempotency key, so the capability returns an existing issue instead of creating a second one. After success the form is cleared.

Evidence is simulated: `apps/web/test/image-issue.test.tsx` runs the component against a fake Core and a fake WebSocket (preview equals payload, exact posted body, pending/declined/success/error, secrets blocked before any request, hostile text inert, oversize and wrong-type images refused). No real GitHub, account, token, screen or approval card was involved. Interface strings (`focus.issueDraft.*`) are English plus nine machine-translated, unreviewed locales.

**Linear and Jira creation (built, text only, fake-tested).** The `issues` capability has `linear.issue.create` and `jira.issue.create` (`external`, confirmed per call, own write-only credentials, host pinned to `api.linear.app` / the owner's `*.atlassian.net` site, no redirects, 15 s timeout, bounded reply, fixed errors, Core audit entries). They are documented in [creating tasks](capabilities/creating-tasks.md) and tested only against a fake `fetch` (`capabilities/issues/test/create.test.ts`); no real Linear workspace or Jira site was contacted. The mounted `ImageIssueSection` (an image you already have) still offers GitHub only; the screenshot flow below drives the Linear and Jira commands.

**Still unbuilt:** nothing real was ever captured (the macOS region-capture adapter below was never run on a real Mac), and nothing real was ever created or attached: Linear and Jira creation and image attachment are built (see below) but only fake-tested, and a GitHub image attachment is impossible to build honestly because GitHub has no documented upload endpoint.

## Screen-region capture (mounted, macOS only, never run for real)

`ScreenshotIssueSection` (`apps/web/src/components/ScreenshotIssueSection.tsx`) is mounted in Settings after the image flow and wraps the capture/annotate/redact `ScreenshotIssue` over Core. It is backed by the built-in `screen-region` capability (`capabilities/screen-region`, command `capture_region`), which is installed but never enabled until the user enables it.

- **The adapter.** On macOS only, `capture_region` runs the stock `/usr/sbin/screencapture` through `execFile` with the fixed argv `["-i", "-s", "-t", "png", <file>]` (interactive, mouse selection only, PNG). No shell, no PATH lookup, no caller input: the command's input schema is an empty object, so a caller cannot pass a path, region, window id or flag. The only variable is the file name, a random 128-bit hex name inside a directory created for this capture (`mkdtemp`, checked to be mode 0700, owned by the user and not a link).
- **Never silent.** The command is `execute` with the `screen_capture` permission. Core confirms that per action even when the permission is granted (`ALWAYS_CONFIRM`), so the person approves in Approvals, then the system's own selector appears and the person drags a region. Nothing is captured unless they do. Whole-screen and window capture are not offered (`-s`, not `-w` or `-S`).
- **Cancel.** Pressing Esc leaves no file and exit code 0; that is a successful `{status: "cancelled"}` result and the page shows a notice, not an error. A non-zero exit, a program that cannot start, or the hard timeout (120 s; the program is killed with SIGKILL) are failures with fixed messages that contain no path, argv or program output.
- **Validation.** The file must be a regular file (a symlink is refused), at most 5 MiB (checked by size before reading and again on the bytes), and a whole PNG (signature, IHDR first, width and height 1 to 16,384, IEND last). Pixels are not decoded. The directory and file are removed on every path: success, cancel, timeout, abort, bad image, oversize, error.
- **Returned to the caller only, bounded.** The image goes back in the operation result as base64 (`mime`, `width`, `height`, `bytes`, `image`), never as a path. Core keeps operation records in memory, so the capability blanks `image` in place after 60 seconds, or when the capability is disabled, and sets `expired`. The page checks the signature and the 5 MiB cap again and keeps the image in page memory only; it is never saved or uploaded.
- **Other platforms** report `{status: "unsupported", platform}` without running anything or touching the disk, and the capability's health is degraded. No `grim`, `maim`, Snipping Tool or similar is guessed at.
- **Issue creation from a capture.** GitHub: text only, through `github` `issue.create`. Linear and Jira: text only, through `issues` `linear.issue.create` / `jira.issue.create` (the project field takes a GitHub `owner/name`, a Linear team UUID or a Jira project key; bad values are refused before any request, as is a missing `issues` capability or write credential). The text is cleaned and secret-scanned like the image flow, and every create is Core's own confirmation. The image is never part of the issue itself; redaction fills pixels as before.
- **When the button shows.** Only when Core lists `screen-region` as enabled with `capture_region` and a granted `screen_capture` permission; otherwise a note says why. The macOS Screen Recording permission itself cannot be read from the page or the capability; if it is missing, `screencapture` yields no usable image and the failure is reported.

Evidence is simulated: `capabilities/screen-region/test/screen-region.test.ts` (a fake `Runner` that writes or withholds the file, a real temporary directory, the real capability manager and permission gateway: success, cancel, timeout, abort, bad magic, JPEG, truncated, zero or huge dimensions, oversize and exactly-at-cap, symlink, a non-zero exit with a file, temp directory empty after every path, fixed argv, 0700 directory, unsupported platforms, confirmation required before anything runs, a decline captures nothing, any input rejected, one capture at a time, image blanked after retention) and `apps/web/test/screenshot-region.test.tsx` (fake Core: mounted in Settings, no capture on load, only on the button, Core's confirmation never answered by the UI, cancel notice, decline, emergency stop, timeout, failure, unsupported, expired, non-PNG and oversize images refused, text-only GitHub creation, Linear and Jira refused, secrets blocked). **Nothing ran on a real Mac: the real `screencapture` was never started, no real Screen Recording permission was granted or observed, no real region was dragged and no real image was produced, and no real issue was created.** `capabilities/screen-region/src/real.ts` (the `execFile` runner) is never exercised by any test. Interface strings (`screenRegion.*`) are English plus nine machine-translated, unreviewed locales.

## Attaching the redacted screenshot (Linear and Jira only, fake-tested)

After a Linear or Jira issue is created from a capture, the page offers an optional second step. **GitHub never gets it**: GitHub has no documented REST endpoint for uploading an image to an issue, and Phoenix does not use the undocumented endpoints the web UI relies on.

1. **Show what would be attached.** The page flattens the current image (redactions drawn last), checks it is a whole PNG of at most 5 MiB, hashes it, and shows the tracker, the issue key, the generated file name (`phoenix-screenshot-<12 hex>.png`, never typed), the byte size and the first 12 hex characters of the SHA-256. Nothing is sent.
2. **Confirm.** A checkbox ("Yes, upload this image to Jira/Linear") enables "Request approval and attach". Pressing it flattens the image again; if it no longer hashes to what was shown, nothing is sent and the page says the image changed.
3. **Core asks again.** `issues` `jira.issue.attach` / `linear.issue.attach` are `external` commands, so Core raises its own approval card (issue key, file name, size and hash prefix) and audits it; a decline, the emergency stop or a timeout is shown as an error and the issue stays text only. The UI never calls `/api/confirmations`.

How the commands work, the Linear signed-URL allow-list (`storage.googleapis.com` and single-label `<bucket>.storage.googleapis.com` over https, no redirects, credentials never sent there, the URL never logged or returned), the limits and the errors are in [creating tasks](capabilities/creating-tasks.md#attaching-a-screenshot-jiraissueattach-and-linearissueattach-phase-85). Evidence is simulated: `apps/web/test/screenshot-attach.test.tsx` and `apps/web/test/screenshot.test.ts` (fake Core and canvas), `capabilities/issues/test/attach.test.ts` (fake `fetch`) and `core/runtime/test/issue-attach-wiring.test.ts` (a real Core, only the body limit). **No real Linear workspace, Jira site, Google Cloud Storage bucket, account or screenshot was involved.** Interface strings (`focus.screenshot.attach.*`, `screenRegion.*`) are English plus nine machine-translated, unreviewed locales.

## Integration requirements

- Focus delivery is wired through Core's authenticated focus routes and the dedicated notification WebSocket channel. The source event's `requires_action` value is retained only for live delivery; it is not added to durable notification storage.
- The macOS region-selector adapter exists (`capabilities/screen-region`, never run on a real Mac); other platforms have none and report unsupported. Do not substitute whole-screen capture. `ScreenshotIssue` (the annotate-and-redact component) is rendered only when Core reports that capability enabled with a granted `screen_capture` permission. Capture and creation are mutually exclusive in `ScreenshotDraft`; annotation is rejected during either operation, so a pending capture cannot replace the image under an approval.
- Linear and Jira creation and image attachment exist as `issues` `linear.issue.create`, `jira.issue.create`, `linear.issue.attach` and `jira.issue.attach` (approval and audit through Core, fake-tested). GitHub has no attach command. An unsupported destination must fail visibly, not silently omit an issue or upload in the background.
- `ScreenshotIssue` (capture, annotate, redact) is mounted through `ScreenshotIssueSection` in Settings (macOS capture only; see the next section). `ImageIssueSection` is the other mounted flow and uses no capture. Never test using real capture, OS focus changes, or external issue creation.
