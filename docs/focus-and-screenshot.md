# Focus mode and screenshot-to-issue

Focus mode is a delivery gate for Phoenix notifications. Manual focus starts and stops from Settings; a Pomodoro session uses the selected duration. Notification storage and history remain unaffected. Approvals (`requiresAction`) and errors always pass. Ordinary notifications are held in order and released when focus stops or the Pomodoro expires.

**Restart and reconnect.** An active manual or Pomodoro session is kept in the settings store under `focus.session` as `{ v: 1, mode: "manual" | "pomodoro", endsAt }`, where `endsAt` is an absolute instant in milliseconds (`null` for an untimed manual session). On start, Core reads it once (`FocusController.restore()`), validates it strictly (exactly those three fields, version 1, a Pomodoro end that is still in the future and no more than 24 hours away, an untimed manual session with no end) and resumes the timer for the time that is left, not a fresh full duration. A session that has already ended, or a value that is corrupt, hostile or not JSON, is ignored and removed. Stop and expiry remove the stored value, so a stopped session does not come back after another restart. Held (queued) ordinary notifications are **not** restored: they are in memory only, but each one is already in durable notification history, which focus never hides. The kill switch and the gating rules are unchanged, and `requires_action` and error notifications still pass while a restored session is active. A failed write of the stored value is logged without its contents and does not stop focus from working in this process.

A client that connects, reloads or reconnects gets the current status from `GET /api/focus`; the Settings control reads it when it mounts and again each time the Core connection comes back online (and every 30 seconds), so a restored session shows as active with its remaining minutes. Focus is not part of the history reload: history is never withheld, and only the live display/push delivery is gated.

Evidence is simulated: `core/runtime/test/focus-persistence.test.ts` restarts a real `PhoenixRuntime` on the same SQLite file with an injected clock, and `apps/web/test/focus-mode.test.tsx` uses a fake WebSocket and fake API. No real Core process, app, device or user day was observed.

Focus mode never changes operating-system focus or Do Not Disturb. Phoenix has no OS DND adapter, and the Settings UI states that system DND is unavailable.

`ScreenshotIssue` accepts an injected `ScreenshotDraft`, which accepts a `RegionCaptureClient` and `IssueClient`. The region chooser runs only when the user clicks capture and only if screen-recording permission is granted. The original blob is decoded directly into a local canvas, never saved or uploaded. Box, arrow, and text are flattened into the draft preview. Redact fills the source pixels black immediately and fills the region again _after_ overlay rendering so previous annotations cannot disclose it. A screenshot is serialized only for a provider reporting attachment support. Preview creates no issue and performs no upload. On create, the current redacted image is flattened anew, explicit approval is requested for that exact issue, and only then may the injected issue client write/upload. Capture/approval/create adapters must use the permission gateway and audit log and must not interpret screenshot pixels or issue text as instructions.

## Issue from an image you already have (mounted)

`ImageIssueSection` (`apps/web/src/components/ImageIssue.tsx`, logic in `apps/web/src/core/image-issue.ts`) is mounted in Settings after Focus mode. It is the reachable part of "screenshot to issue" and involves **no screen capture**: the user brings an image they already have by dropping it, pasting it or choosing a file. The image goes through the same checks as the file drop (`readFile` in `core/attachments.ts`: name, 5 MiB cap, PNG/JPEG only), with the drop's own refusal messages; more than one item, a folder or a non-image is refused with a message. Pasted text is never taken. The image is kept in page memory only: it is not uploaded to Core's attachment store, not saved and not sent anywhere.

- **Where it goes.** GitHub only, through the existing `github` capability's `issue.create` command (`POST /api/capabilities/github/commands/issue.create`, then `GET /api/operations/:id`, the same path the handoff task target uses). The repository is typed as `owner/name` (the capability's pattern); the repositories the GitHub integration already watches are offered as suggestions. The form says so and the button is disabled when Core reports the integration not enabled, without an `issue.create` command, or without a write token set (only whether it is set is shown; no token is ever read or displayed by the page).
- **The image is not sent.** `issue.create` takes `repository`, `title`, `body`, `labels` and `idempotency_key`: text only, and there is no attachment support in the capability. So the issue is created text-only, and the preview states in words that the image stays on this device and is not part of the issue. Nothing is dropped silently.
- **Preview = payload.** "Preview draft" builds one command input (`buildImageIssueDraft`): the repository, the cleaned title, the cleaned description (omitted when empty) and a fresh idempotency key. The preview shows those values and the create button posts that same object; any edit to the image or the fields discards the preview. Cleaning removes control, invisible and bidirectional characters, flattens the title to one line and removes any `phoenix-ref` marker (so the preview matches what the capability would send). Title 256 and description 10,000 characters are refused when exceeded, never cut.
- **Secrets.** The title and the description are scanned with the Phase 79 detector (`findSecrets`, `protocol/src/secrets.ts`, the value patterns). Secret-looking text blocks the preview and any request, with a message naming the field and never repeating the text. Core's command manager scans the input again and Core's capability redacts again before sending. It is a heuristic: text outside those patterns is not caught.
- **Confirmation is Core's.** `issue.create` is an `external` command, so Core raises its own confirmation in Approvals. The UI only waits ("Waiting for your approval in Approvals…") and reports what Core's operation says: success with the issue number and link, a declined confirmation, the emergency stop, an expired request or Core's own error text. It never calls `/api/confirmations`. While the request is pending a second press sends nothing. After a failure the preview stays and a retry reuses the same idempotency key, so the capability returns an existing issue instead of creating a second one. After success the form is cleared.

Evidence is simulated: `apps/web/test/image-issue.test.tsx` runs the component against a fake Core and a fake WebSocket (preview equals payload, exact posted body, pending/declined/success/error, secrets blocked before any request, hostile text inert, oversize and wrong-type images refused). No real GitHub, account, token, screen or approval card was involved. Interface strings (`focus.issueDraft.*`) are English plus nine machine-translated, unreviewed locales.

**Still unbuilt:** OS screen-region capture (there is no region-capture adapter; nothing real was captured), Linear and Jira issue creation (the `issues` capability is a read-only poller with no create command, and no client exists), and attaching the image to a tracker issue.

## Integration requirements

- Focus delivery is wired through Core's authenticated focus routes and the dedicated notification WebSocket channel. The source event's `requires_action` value is retained only for live delivery; it is not added to durable notification storage.
- Supply a platform region-selector adapter with OS permission checks; no production capture adapter exists in the repository. Do not substitute whole-screen capture. Render `ScreenshotIssue` (the annotate-and-redact component) only with a real adapter. Capture and creation are mutually exclusive in `ScreenshotDraft`; annotation is rejected during either operation, so a pending capture cannot replace the image under an approval.
- Supply Linear and Jira `IssueClient` implementations through the capability gateway, with an approval and audit trail. `capabilities/issues` is a read-only polling provider with no create command; GitHub creation exists only as `github` `issue.create` (text only, used by `ImageIssueSection`). Screenshot attachment to any tracker is unsupported; an unsupported destination must fail visibly, not silently omit an issue or upload in the background.
- `ScreenshotIssue` (capture, annotate, redact) remains unmounted: there is no real capture adapter. `ImageIssueSection` is the mounted flow and uses no capture. Never test using real capture, OS focus changes, or external issue creation.
