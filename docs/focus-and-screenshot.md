# Focus mode and screenshot-to-issue

Focus mode is an in-memory delivery gate. The host must feed **each notification** through `FocusController.receive()` before displaying or pushing it; durable notification storage is unaffected. Approvals (`requiresAction`) and errors always pass. Ordinary notifications are held in order and released when manual focus is off and the read-only OS DND reader gives an affirmative "off" reading; if DND was on and the reading becomes unknown, notifications keep being held. A Pomodoro timer uses an injected clock; it never changes system DND. Held notifications disappear on process restart unless the host persists and replays them.

`ScreenshotIssue` accepts an injected `ScreenshotDraft`, which accepts a `RegionCaptureClient` and `IssueClient`. The region chooser runs only when the user clicks capture and only if screen-recording permission is granted. The original blob is decoded directly into a local canvas, never saved or uploaded. Box, arrow, and text are flattened into the draft preview. Redact fills the source pixels black immediately and fills the region again _after_ overlay rendering so previous annotations cannot disclose it. A screenshot is serialized only for a provider reporting attachment support. Preview creates no issue and performs no upload. On create, the current redacted image is flattened anew, explicit approval is requested for that exact issue, and only then may the injected issue client write/upload. Capture/approval/create adapters must use the permission gateway and audit log and must not interpret screenshot pixels or issue text as instructions.

## Integration requirements

- Inject an OS DND **read-only** reader and system clock into `FocusController`, wire the notification delivery sink through `receive`, expose controller state to `FocusMode`, and dispose it when the host shuts down. No new persistence schema is needed. The existing seams are the web client's `notificationCreated` emitter (`apps/web/src/core/client.ts`, fed by `notification.created` events from `core/notifications`) for display/push delivery, and a host-supplied `requiresAction` mapping: the stored `Notification` type does **not** carry the source event's `requires_action` flag, so the host must derive it (for example from `eventType` such as `security.confirmation.requested`, or by adding the flag to the notification payload) before calling `receive`. Until then, approvals are not distinguishable from ordinary notifications and would be held. A notification previously held under the same `id` is removed if it later passes through as an approval or error; the host remains responsible for deduplicating already-delivered notifications. `dispose()` drops held notifications and ignores in-flight OS reads.
- Supply a platform region-selector adapter with OS permission checks; no production capture adapter exists in the repository (no desktop screen-capture or OS DND reader was found). Do not substitute whole-screen capture. Render `ScreenshotIssue` only with a real adapter. Capture and creation are mutually exclusive in `ScreenshotDraft`; annotation is rejected during either operation, so a pending capture cannot replace the image under an approval.
- Supply provider-specific `IssueClient` implementations for GitHub, Linear and Jira through the existing capability gateway, with an approval and audit trail and explicit screenshot-attachment support. `capabilities/issues` is a read-only polling provider; Phase 26 does not provide the write/attachment paths, so no production provider client is supplied here. The approval step receives a copy of the draft that is the one later passed to `create`; unsupported destinations must fail visibly, not silently omit an issue or upload in the background.
- Mount `FocusMode` and `ScreenshotIssue` in the host UI. Translation namespace `focus` exists in English and nine locales; locale strings are machine-translated and need review.

Without those adapters and host wiring, these components are injectable workflows, **not** a live OS capture or external issue integration. Today `FocusController` is not in the notification delivery path, no OS DND reader, region-capture adapter or Linear/Jira/GitHub issue client with create exists, and `FocusMode` and `ScreenshotIssue` are not mounted anywhere; nothing real was captured. Never test using real capture, OS focus changes, or external issue creation.
