## Goal

Give Fawkes context by dropping a file on it or dragging it onto a window.

## Tasks — parity with Coucou

- [x] Drop a file on Fawkes, then ask a question about it: drop on the chat box or on the Pet Panel overview's "Drop files on Fawkes" target, plus an "Attach files…" picker; held in Core's memory (`core/runtime/src/attachments.ts`, `core/api/src/attachment-routes.ts`), asked through `POST /api/attachments/ask` with the prompt from `ai/context/src/attachments.ts`. Tests: `core/runtime/test/attachments.test.ts`, `core/runtime/test/attachments-prompt.test.ts`, `apps/web/test/attachments.test.tsx` ("dropping on the chat box", "Ask about attachments", "the Pet Panel drop target"). The floating and island windows take a native drop too (see "Native file drop" below). The drags in the tests are synthetic events built by the test; no real Finder drag was made.
- [x] Send it by email (draft only, the user sends): `buildMailto` / `openMailto` (`apps/web/src/core/attachments.ts`, form in `Attachments.tsx`) and the `open_mailto` Tauri command (`apps/desktop/src-tauri/src/mailto.rs`, `lib.rs`). No recipient by default, nothing is sent by Phoenix, the user edits and sends from their mail app. Tests: `apps/web/test/attachments.test.tsx` ("draft email"), seven Rust unit tests in `mailto.rs` (scheme, length, control and bidi characters). No mail app was opened for real, and `open_mailto` is not covered by `tests/lifecycle.rs`.
- [ ] Drag Fawkes onto a window to attach that window as context (macOS). The drag itself is not built (no drag handling in `apps/desktop`, no way to know what window a drag ends on). Built instead, tested with fakes only: a user-started **Attach a window…** button in the Chat tab (`apps/web/src/components/WindowCapture.tsx`, `apps/web/src/core/window-capture.ts`) calling `POST /api/attachments/window/capture`. Core asks the person to confirm (an `execute` action in the confirmation list, text fixed, no window content in it), waits 4 s so the person can bring a window to the front, then runs ONE fixed `osascript` (`core/runtime/src/window-capture.ts`: one `-e` per line of a constant script, no shell, no input of any kind in the script or argv) that asks System Events for the frontmost application, its front window's title and its static-text, text-area and text-field values. Bounded: 5 s deadline (a timeout is an error, never a partial answer), 512 KB of output, 100,000 characters kept (cut and marked), control, bidi, zero-width and line/paragraph separator characters stripped. The reader never returns Phoenix's own window (bundle id `dev.phoenix.desktop`, app name `Phoenix`, or a window titled Phoenix, which also covers a browser tab) and answers `accessibility_not_granted` when macOS denies Accessibility or Automation, with one run and no retry and no settings pane opened. The text is shown to the person in the page with an **Attach this text** / **Discard** choice; nothing is stored by the capture, and only Accept posts it to the tray as origin `window` (3 per tray, then the normal 10 / 8 MiB limits). `POST /api/attachments` also refuses window text that the agent secret detector flags (`SECURITY_POLICY_BLOCKED`, kinds named, values never). Tests: `core/runtime/test/window-capture.test.ts` (fake exec: success, denied, timeout, oversize, hostile text, injection text inert, own window excluded, fixed argv), `core/runtime/test/window-capture-api.test.ts` (confirmation required and declinable, kill switch, off macOS, body ignored, one at a time, cap of 3, secrets), `apps/web/test/window-capture.test.tsx` (nothing posted before Accept, Discard posts nothing, text not markup). **Nothing ran on a real Mac, against a real window, or with a real Accessibility grant**: the AppleScript is unrun, and whether `entire contents` of a real window yields useful text (it is slow or empty for some apps, and web content and Electron apps may expose little) is unknown.

## Tasks — Phoenix improvements

- [x] Folders and images with local vision when available: a dropped folder is walked in the browser (entry API, dot-directories, `node_modules` and `.git` skipped, 200 files at most) and sent as a listing with text; an image is described by a local Ollama vision model and the description is what is asked about. Tests: `attachments.test.tsx` ("a folder: walked with the entry API…", "an image: read with FileReader…"), `attachments.test.ts` ("folder listings", "images need a local vision model", driven by a fake network). The local vision path was only run against a fake Ollama: no vision model was installed or run. Phoenix does not capture screenshots; a screenshot only counts if it is dropped or pasted as an image file. Paste is handled on every drop surface (see Paste below); the web pages post origin `paste` for it.
- [x] Context stays local unless an external AI purpose is opted in. Built stricter than written: the Ask purpose is fixed and deliberately outside the sensitive-cloud allow-list, so no cloud provider is used even with every opt-in (`attachments.test.ts` "asking is local only": with every opt-in on and Ollama down no cloud request is made, and a cloud route chosen by the user is still refused by the gate). Whether a user may ever opt attached files into cloud AI is an owner decision ([gap register](../gaps.md)).
- [x] Attached context is visible and removable before anything is sent: the tray lists each attachment with a "Local only" badge and a Preview, Remove and Clear all, and the Ask button names how much will be sent and where (`attachments.test.tsx` "the tray", "removal before anything is asked", "shows how much will be sent and where").

Not demonstrated. `attachments.test.ts` gets an answer through Core with a fake Ollama network, and `attachments.test.tsx` drives the drop with synthetic events; no real Finder drag was made and no real local model answered a question about a real dropped file.

## Implementation notes

- **Storage.** In memory only: at most 10 attachments, 8 MiB in total, 200,000 characters of text, 5 MiB per decoded image, a one-hour lifetime judged by an injected clock, cleared by the emergency stop; no event, audit row, log line or database table holds content (`attachments.test.ts` "content is held in memory only"). `POST /api/attachments` accepts a body up to `ATTACHMENT_BODY_MAX_BYTES` (7 MiB); every other route keeps 256 KiB (`attachments-body-limit.test.ts`).
- **Prompt.** Attached content is data between per-call nonce delimiters, stripped of control, bidi and zero-width characters; the reply is cleaned and refused when empty or too long (`attachments-prompt.test.ts`).
- **Native file drop (floating and island windows).** Both windows keep Tauri's default drag-and-drop handler on (no `dragDropEnabled`/`disable_drag_drop_handler` change anywhere; the main web app is a browser tab, not a Tauri window, so its HTML5 drops are untouched), so the OS drop reaches the shell as a `DragDropEvent` and the page gets no HTML5 `drop` there. `apps/desktop/src-tauri/src/file_drop.rs` takes only those two window labels (the loopback dictation pill and any other window are ignored). A drop is looked at off the event loop: at most 3 entries (the rest are only counted), each absolute, without `..` or control characters, at most 4,096 bytes, a regular file by `symlink_metadata` (a symlink, directory, FIFO, device or socket is refused) and at most 5 MiB (`MAX_FILE_BYTES`, equal to `DROP_LIMITS.imageBytes`; a web test compares the two constants). Accepted files go into an in-memory allow-set with a number, a 60-second lifetime and the label of the window they were dropped on; the page is sent (`file-drop://drop`, to that window only) only numbers, names and sizes, **never a path**. The page asks for each number with `read_dropped_file(id)`: the entry is removed on the first ask, an unknown, used, expired or other-window number reads nothing, the shell re-validates the path, opens it, compares device and inode with what was checked (a path swapped for another file or link in between is refused) and reads at most the cap plus one byte. The command is on the Fawkes/island capability only (not the pill's). Nothing logs a path or content. The page (`apps/web/src/commands/file-drop-shell.ts`, `core/native-drop.ts`) turns the bytes into a `File` and hands it to the existing `useAttachmentUpload` -> `readFile` -> `POST /api/attachments` with origin `drop`, so type, name and size checks, Core's validation and every message are the existing ones. New strings (nine locales, machine-translated and unreviewed): a folder cannot be dropped here (no entry API for a native drop) and "only the first 3 files are used". Drag-over feedback: `file-drop://hover` shows "Drop to attach." and a dashed outline; the result appears in a status line (floating) or in the island label/body, and keeps the island awake for 8 seconds. Tests: 19 Rust unit tests in `file_drop.rs` (path table, symlink, directory, oversize at and over the cap, FIFO and device on Unix, count cap, TTL boundary, one-shot, window binding, replacement, swapped file), the lifecycle test "a dropped file is announced without its path and read once by its window only" (mock runtime, through the real command path), and `apps/web/test/native-drop.test.tsx` (24 tests: floating and island handlers with a fake shell bridge, origin `drop`, existing error messages, Core refusal, bridge parsing). Each key line was reverted once to see the matching test fail (window check, one-shot removal, TTL purge, count cap, `symlink_metadata`, origin, the `earlier` notes), then restored.
- **Mailto.** The page builds the `mailto:` URL (subject, body and an optional typed recipient, percent-encoded, 1,900 characters at most) and the shell checks only that it starts with lowercase `mailto:`, is at most 2,000 characters and contains no control, bidi or zero-width character. It does not check the recipients or headers, so a window page that builds `bcc=` can put an address in the draft; the user still has to press send.
- **Paste.** Every `DropZone` (chat box, Pet Panel overview) takes a user paste (`onPaste` → `collectPasted` in `apps/web/src/core/attachments.ts`; the clipboard is read only inside that event) and posts origin `paste` to the same `POST /api/attachments`. Pasted files and images go through exactly `readFile`'s checks (name, 5 MiB image, text type and size) and Core's validation, with the same messages and chip UI; Core caps pastes at 5. A paste is intercepted only when it carries a file, or when it is plain text of at least 20,000 characters (`PASTE_TEXT_MIN_CHARS`) pasted outside an input, textarea or select (it becomes `pasted-text.txt`); anything else, including every text paste into the message box, is left to the browser. Tests: `attachments.test.tsx` ("pasting on the chat box", "a pasted file on the Pet Panel Overview…", "collectPasted…"), driven by synthetic paste events; no real clipboard, screenshot tool or browser paste was used. No screenshot capture is built.

What was not done or not run: a real native drag onto the floating or island window (only the shell's event handling, the allow-set, the file checks and the page are tested; the OS delivering a `DragDropEvent` for a real Finder/Explorer/file-manager drag was never observed, nor on Linux or Windows), folders through a native drop (refused with a message), a real Mac Accessibility window read (the script was never run) and the drag gesture, a real Finder drag, a real local model answer, any local vision model, a real mail app opened by `open_mailto`. Open items are in the [gap register](../gaps.md).

- **Window capture.** Safe-by-construction parts: a constant script and argv, a 5 s deadline, bounded output, sanitised text, Phoenix's own window excluded, a Core-raised confirmation before every read, review before the tray, no timer and no agent entry point (it is not a capability command or an agent tool). Residual risk: the route needs only the session token, and the confirmation prompt is shown in Phoenix's own UI, so a program holding the token can start a capture and can approve its own prompt through `POST /api/confirmations/:id` (the Phase 63/65 person-versus-agent problem). It can read the text of whichever window is in front once the Accessibility grant exists, but it cannot put it in the tray (the page does that on Accept; a token holder could also post it, as it can post any attachment) and a capture never leaves the device (asking is local only). The fixed 4 s lead is Phoenix choosing the window for the user, not the user pointing at it.

## Notes & risks

- Phoenix uses its own assets; nothing from Coucou's asset list (names, Mochi, sounds, icons, media).
- Any copied or closely translated MIT code keeps its notice and goes in the licence inventory.
- Side effects go through the permission/tool gateway and the audit log; untrusted content is data, never instructions.
