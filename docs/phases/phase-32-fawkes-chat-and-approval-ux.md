## Implementation notes

All UI, in `apps/web`; no backend changed. It is built against the contracts of Phase 29 (`/api/memory/ask`, `/api/ai/status`) and Phase 31 (`/api/agent/*`, the optional `task_id`/`risk`/`target`/`preview`/`evidence_ids` on `/api/confirmations`).

**Where things are**

- `components/Chat.tsx` (Chat tab), `components/AnswerView.tsx` (a memory answer, shared with the Memory tab), `components/TaskView.tsx` (a task card and the "Current task" section), `components/Approvals.tsx` (the approvals queue), `components/AutomationSettings.tsx` (Settings, `agents.enabled`).
- `core/chat-store.ts` + `core/chat.ts`: the conversation, `core/agent.ts`: plain-language labels, `core/hooks.ts`: `useAgentSettings/useAgentTasks/useAgentTask` (live resources), `core/format.ts`: `safeHttpUrl`.

**Chat.** Enter sends, Shift+Enter is a newline (not while an IME composes), 500-character cap (the API's `MAX_QUESTION_CHARS`), one request at a time. A reply lists the stored facts first (domain, source, `source_ref`, observed date, sensitivity), then the interpretation labelled "Generated by <processed_by>, not a stored fact." or "No AI was used.". `source_ref` is rendered as text; it becomes a link only when it parses as a plain http(s) URL without credentials, opened with `rel="noopener noreferrer"`. A failed request is an `alert` that names what failed. "Diagnose a CI failure" opens a small form (owner/name, optional run id; validated with the same pattern as the agent) that posts `POST /api/agent/tasks` and puts the task into the conversation as a card that follows the run live.

**Conversation history is in memory only.** It lives in a `ChatStore` in the page (one per client). It survives switching tabs and closing the panel and is gone on reload. Nothing is written to local/session storage or sent anywhere beyond `POST /api/memory/ask` and `POST /api/agent/tasks`. (Test: both storages stay empty.)

**Personality boundary.** The page invents no state, work or confidence: the only "busy" text appears while a request is really in flight; the line "Fawkes is <state>" is Core's real pet state through `visualFor`; confidence is shown only where Core supplies a number (a task's `evidence_coverage`, labelled "computed by Phoenix"); the model's own confidence word is shown only with the sentence that Phoenix did not verify or use it. Error replies state what failed.

**LISTENING.** `useDisplayedState` (`core/context.tsx`) now returns LISTENING while the message box has focus and text and no request is in flight, **only over IDLE** (it never hides an error, an approval, recording, real work, or OFFLINE). It is a display override of this page: Core is not told, so another window (for example the floating desktop pet) does not show it, and nothing typed leaves the page before Send.

**Current task.** The Overview and Chat show the active run: state in words (Created / Ready / Running / Waiting for your approval / Checking the result / Finished / Failed / Cancelled), the steps (tool, status, risk, policy decision), evidence with excerpts and "Truncated" markers, diagnosis claims with grounded/not grounded and rule/model badges and evidence ids that open and highlight the evidence, proposals labelled advisory, the verification checks, and a Cancel button. It reloads on `agent_run.*` and `security.confirmation.*` events (the existing `useLiveResource` emitters); there is no timer.

**Approvals.** Each pending confirmation is an explanation card: what will happen (capability, command, effect), the preview, the target, the risk as a text badge (Low/Medium/High/Critical, also distinguished by border style, not colour alone), permissions used, the task and evidence ids when present, and when it expires. A missing preview, target or risk is shown as "No preview was provided by this capability." etc., never as a blank. Approve/Reject have accessible names `Approve: <summary>` / `Reject: <summary>`. High and Critical need a second explicit step: a checkbox "I understand this will <effect>" enables Approve (no timers). Reject needs no extra step. The queue is a list: Up/Down move between cards, there are no global shortcuts, and after a decision focus moves to the next card (else the previous one, else the section heading). Results are announced in an `aria-live="polite"` region that exists before the result.

**Floating shell.** The floating window is 200x220 px and renders only the pet and a bubble, so the panel does not fit in it. Instead, a click on Fawkes while WAITING now opens Phoenix at `#/panel/overview` (`routeFor`), and the main app opens the Pet Panel on that tab (`#/panel/<tab>`), where the approvals are. The floating app itself still renders (test).

**Settings.** "Automation" binds `GET/POST /api/agent/settings` (`agents.enabled`), off by default, with a plain explanation.

## Not done / limits

See `docs/gaps.md` rows for Phase 32. In short: LISTENING is local to the page; approval cards were verified in unit tests only (a real Core has no write capability for agents); no screen-reader and no visual review; the floating window does not host the chat.
