# Developer preview programme — operating procedure, not a release announcement

This is the Phase 43 plan, not evidence that an external cohort was recruited or that any preview was published. The four stages in [Technical Specification Suite §13](../vision/Phoenix_Technical_Specification_Suite_04-14.docx) are sequential gates, not dates. The release owner records a decision and the evidence below before advancing; a failed gate stops promotion. Do not publish a package, invite anyone or describe a stage as complete on the strength of this document alone.

## Candidate bundle and limits

Produce one immutable candidate from a recorded commit, with build instructions, checksums, platform/architecture, source and corresponding source offer, `LICENSE`, `THIRD_PARTY_NOTICES.md`, a dependency/asset inventory, installation and rollback instructions, known limitations, test/gate reports and support/security contacts. Record exactly which executable and SDK artifacts are present; an installable release archive does **not** currently follow from `pnpm start`. For an internal source checkout the proposed bundle comprises Core plus Fawkes web UI (desktop only on separately verified macOS builds), Event Protocol v1, `@phoenix/sdk` and the external-capability example, GitHub and Kage capabilities, local memory, bounded agent runtime, permission/policy gateway, and offline evaluation harness. Exercise each against an isolated test data directory before marking it included. GitHub needs explicitly configured credentials; Kage needs a separately running Kage service and explicit recording permission. Neither is bundled as a usable external service. Record optional local AI/model prerequisites and do not turn on cloud AI by default. Include Git/terminal and other developer integrations only when separately inventoried and verified. The SDK package is currently workspace-private (`sdk/capability/package.json`); publishing it is a distinct release action, not implied by this plan.

The source checkout route is [README getting started](../../README.md#getting-started): Node ≥22.13 and pnpm 10, `pnpm install`, `pnpm start`, then <http://127.0.0.1:4870>. Do not circulate `.phoenix/dev/session.token`; use a fresh profile and the Settings capability and privacy panels. For capability authors follow [Building a Capability](../capabilities/getting-started.md), `pnpm dev:core` plus `pnpm tsx sdk/capability/examples/hello-external.ts`, then explicitly enable Hello. Use test fixtures and a local mock/simulator to avoid real GitHub writes, production operations, Kage recordings, or cloud-model calls. `pnpm simulate list` lists scenarios. Run the evaluation offline via `npx vitest run ai/evaluation`; the proposed v1.0 gate is _not_ a CI release blocker today (see [release gates](../release-gates.md)). CI also runs typecheck, lint, tests, web build, macOS Rust checks, vulnerability/notices and secret scans ([workflow](../../.github/workflows/ci.yml)); a green CI is necessary but not proof of an installable distribution.

### Local artifact inspection (not a release)

For local artifact inspection **after** a real desktop installer has been built with `corepack pnpm --filter @phoenix/desktop build`, run `node docs/preview/check-candidate.mjs apps/desktop/src-tauri/target/release/bundle/<platform>/<actual-installer> [sdk/capability/<actual-sdk-tarball>.tgz]` from the checkout root. Supply existing file paths; the script checks nonempty recognized installers/archives and prints SHA-256 and byte counts without signing or publishing. A `target/debug/phoenix-desktop` executable is **not** an installable bundle and must not be passed off as one. No installer currently identified under `apps/desktop/src-tauri/target/**/bundle/`; desktop packaging, clean-install/platform verification and signing remain pending, as do GPL corresponding source/notices/licence review and release-owner decision. `npm pack ./sdk/capability --pack-destination ./sdk/capability` produces a local SDK tarball only after the SDK build and isolated-consumer check documented in [SDK API](../capabilities/sdk.md); it does not distribute a preview.

Before an owner distributes anything, record the signing identity and chosen platform signing/notarization policy (or explicitly approved unsigned internal-only candidate), GPL-3.0-or-later source availability, generated third-party notices, the licence inventory, and an independent clean-install and rollback record for each promised platform. This local checksum script attests none of these, and no external cohort or support response has been measured.

A stage may remain internal indefinitely. Define before starting each cohort: size, duration, platforms, opt-in and feedback channel, supported features, severity/response owner, exit sample, cutoff and privacy/retention of submitted evidence. Numbers of users, error rates and timelines must be _measured_, never filled with aspirational data. Do not collect automatic telemetry: request opt-in reports, minimize identifiers, never request raw tokens, private repository content or transcripts. The existing README privacy text is stale in places; verify actual model/network behavior in the candidate instead of relying on that text.

Evidence belongs in a release issue or retained build artifacts with access controls, not unredacted personal data in git. Link logs by immutable digest and command + environment; state observed counts and denominator. Include failed attempts, not only successes. Separate offline scripted tests from local real-model evidence and human/external review; never label a proposed gate an approved one. Owner explicitly signs accept/reject with rationale, open limitations and expiry. A new commit or dependency/manifest change invalidates affected evidence and requires rerun.

## Install → use → feedback → reproduce → fix → regression → release

1. **Install:** record commit, lockfiles, OS/arch, Node/pnpm (and Rust for desktop), checksum, clean-profile startup, upgrade path and auth/token setup. Keep the session token local. Do not promise Linux/Windows desktop support; [desktop status](../../apps/desktop/README.md) records macOS-only checking.
2. **Use:** follow the safe source-checkout path above; enable only required capabilities, inspect requested permissions, verify event/activity and Fawkes state, memory inspection/deletion, and emergency disable. For an SDK integration validate manifest, authenticate external loopback registration, emit only declared events and exercise read-only commands in a fixture. Keep AI off or use explicit local-only settings; obtain consent for any real provider or data.
3. **Feedback:** ordinary bugs or feature requests go in repository GitHub Issues with candidate commit/artifact checksum, OS, expected/actual, minimal redacted steps, observed frequency and diagnostics where safe. The maintainer assigns severity, owner and affected stage, acknowledges and routes regressions to the owning component. Never ask reporters to paste the session token, cloud key, proprietary repository, personal meeting transcript or raw database; scrub exports and obtain consent before sharing.
4. **Security:** for permission bypass, credential/data disclosure, event spoofing, unsafe recording, prompt injection yielding actions or network exposure, **do not open a public issue**. Use GitHub **Security → Report a vulnerability** privately as [SECURITY.md](../../SECURITY.md) specifies; include affected commit and redacted reproduction. Policy states acknowledgement within seven days. Restrict evidence, coordinate disclosure and pause promotion pending assessment. No claim of an external security audit.
5. **Reproduce and fix:** use an isolated test data dir and fixture/no-network configuration. Capture inputs, expected result, relevant redacted audit/diagnostics, version and reproducibility rate; add a failing automated regression that identifies the cause, fix it without weakening approval/security checks, re-run relevant checks in normal development workflow and retest fresh install plus upgrade path.
6. **Regress and release:** link the fix to the issue, test and exact candidate digest; rerun CI and appropriate offline/adversarial gates, refresh licence/dependency and security review on material changes, then repeat upgrade and rollback. Update limitations, migration instructions and ledger; release owner explicitly approves the next candidate. Re-open the stage when a fix changes a public contract or breaks a supported path.

## Candidate release checklist

- [ ] Record exact source/artifact digests, supported platform matrix, clean install and reproducible build evidence; retain corresponding source, licences and notices in every distributed bundle.
- [ ] Review [security threats and gaps](../security-review.md), secret scan, audit/redaction, session-token model, capability isolation, permission approval and kill switch; close or disclose blocking risks with owner sign-off.
- [ ] Record protocol schema and SDK export/manifest baseline, compatibility fixtures across candidate upgrade pairs, API documentation and known limitations. See [v1 verification](../release/v1-verification.md).
- [ ] For each migration, back up local SQLite/profile and settings _offline_, test forward migration on a copy and restart; test downgrade against a disposable copy or restore the original backup. Never assume SQLite migrations are reversible; stop old Core before restore and do not overwrite newer user data with old binaries. Document any irreversible transformations and how to export user data.
- [ ] Verify permissions and external credentials remain scoped after upgrade; disable changed capabilities pending new grants. Rehearse rollback of binaries and profile together, confirm events/memory survive or disclose exact losses; collect the failed-candidate digest and incident response owner.
- [ ] Generate and check `THIRD_PARTY_NOTICES.md` from lockfiles, audit npm/Rust dependencies, update [licence inventory](../licenses/INVENTORY.md) for actual distributed assets and target-specific crates, include GPL source offer and Fawkes CC BY-SA attribution; resolve Linux GTK warnings before Linux distribution.
- [ ] Publish versioned instructions, issue and private vulnerability reporting, support owner/response process, upgrade and rollback, supported features, unsupported platforms, model/provider privacy and known limitations; only then consider stage announcement.
