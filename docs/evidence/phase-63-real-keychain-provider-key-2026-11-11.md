# Phase 63: provider key in the real macOS Keychain (2026-11-11)

Evidence from one run on macOS 27.0.1, Node 22.19.0, an unsigned Node process under the developer's own login keychain. Raw numbers: [`phase-63-real-keychain-provider-key-2026-11-11-raw.json`](phase-63-real-keychain-provider-key-2026-11-11-raw.json). Test: `core/runtime/test/real-keychain-provider-key.test.ts` (`PHOENIX_REAL_KEYCHAIN=1`, macOS only). No value is printed or saved anywhere: fake values are `fake-value-<random hex>` made at run time; this file and the JSON hold a length and a SHA-256 prefix only.

## What ran for real

A `PhoenixRuntime` with `secrets: new KeychainSecretStore()` (production service `phoenix`, the real `/usr/bin/security`), the production routes `POST/DELETE /api/ai/providers/:id/secret`, and the production AI path (`AiService.run`, routed `chat` to a user endpoint) against a recording HTTP server on `127.0.0.1`. The service name is fixed by the store, so every item carries the account marker `kc63-` (`phoenix.ai.kc63-<hex>_api_key`); a sweep of only marked accounts runs before and after and the test asserts none is left. Afterwards `security dump-keychain | grep -c kc63` printed `0`.

## Defect found: silent truncation at 128 characters (fixed)

The old macOS path ran `security add-generic-password -U -s phoenix -a <ref> -w` with the value twice on stdin. Measured on throwaway items (`old_path_add_generic_password_w` in the JSON): lengths 100 and 128 stored whole; 129, 200, 1000 and 4000 all exited **0** and stored exactly **128** characters. The route returned `200 key_set:true`, and the provider then got a cut key (an authentication failure at the provider, no hint why). Real provider keys can exceed 128 characters.

Failing first: the new real test failed on `ascii-129 round trip` against the old code. Fix (`core/persistence/src/secret-store.ts`): the command runs inside `security -i` with the commands on stdin (no value in argv) and the value passed as hex (`-X`), which has no 128 cut and needs no quoting. `security -i` refuses a command line of 4096+ characters (4094 stores, 4096 exits 1), so a value that does not fit is **refused** with `SecretTooLongError` (route: `400`, "The macOS Keychain path keeps at most N bytes for this secret"), nothing is stored and an existing key is untouched. With the account `phoenix.ai.kc63-xxxxxxxx_api_key` the limit is 2009 bytes; for `phoenix.ai.openai_api_key` about 2013. `get` now reads `find-generic-password -g` because `-w` prints a value as hex when it is not plain printable ASCII (a value with non-ASCII characters or a backslash came back as hex); `-g` marks the hex form.

Mutation checks (each restored afterwards): old `-w` path put back: 3 unit tests and the real test fail (ascii-129 round trip); line-limit check removed: unit test fails and the real test sees `500` for 4000 chars; `SecretTooLongError` not mapped to 400: real test sees `500`.

Cannot be told apart: an item already stored truncated by the old build reads back as a 128-character key, indistinguishable from a real short key (`item_stored_truncated_by_old_path`). Anyone who set a key longer than 128 characters before this fix must set it again.

## Not shown

A real cloud provider; a real key; Linux Secret Service; Windows Credential Manager; a signed app and the macOS Keychain access prompt another binary would get (the unsigned Node process created and reads its own items without a prompt); a locked keychain or a keychain with a different default. The values are bytes of a fake key: the provider's reaction to a real key was not observed.
