# Phase 76: real MCP clients against the Phoenix MCP server (2026-11-11)

What this is: the real `claude` and `gemini` binaries on this Mac were pointed at a real in-process Phoenix Core (its MCP listener) with client tokens created through the production owner route, and their model-free MCP commands (`claude mcp add/list/get`, `gemini mcp add/list`) were run. Then the Core side (audit rows, client list) and an observing loopback proxy showed what the clients actually sent.

What this is NOT: no model was called and no prompt was sent to any agent. `claude mcp list` and `gemini mcp list` perform a health check (initialize, and for Claude `tools/list`; Gemini `ping`); neither can call a tool or ask for an approval without a model. So **this does not show that a real client read Phoenix context, nor that an approval was decided in Phoenix**. Those parts of the exit criterion are still unverified.

## Setup

- Machine: macOS 27.0.1 arm64. Node v22.19.0 (`/Users/bluephoenix/.nvm/versions/node/v22.19.0/bin`) for Core, the harness, the bridge and the proxy.
- Real clients: Claude Code `2.1.308`, Gemini CLI `0.17.0`. Cursor and Codex are not installed here (`which cursor codex` prints nothing), so their snippets stay unverified.
- Core: a real `PhoenixRuntime` (`core/runtime/src`), started by a throwaway script `/tmp/p76/harness.mts` (run with `./node_modules/.bin/tsx`), database `:memory:`, no capabilities, session token chosen by the script, API port assigned by the OS. It enabled the MCP listener on **48931** with the production routes `POST /api/mcp/settings {enabled:true,port:48931}`, `POST /api/mcp/clients {name}` and `POST /api/mcp/clients/:id/grants`. Port 47822 was not used (nothing listened on it).
- Two clients: `granted-client` (grants: the five read tools, `request_approval`, `notify`; no memory scopes) and `nogrant-client` (no grants). Tokens were generated by Core (`pmcp_...`, shown once) and are replaced by `<TOKEN>` below.
- An observing proxy `/tmp/p76/proxy.mjs` (loopback 48932 -> 48931, logs request headers (token redacted), body and reply) was used for most runs to see what the client sent; the first Claude runs went straight to 48931. The proxy adds nothing the client does not send; it sets `Host` to the upstream port.
- Isolation: every client run used a throwaway config (`CLAUDE_CONFIG_DIR=/tmp/p76/<dir>`, `HOME=/tmp/p76/ghome`) and a temp project directory under `/tmp/p76`. The user's real `~/.claude`, `~/.gemini`, `~/.codex` were not read or written. Nothing was run with a prompt.
- One aborted first attempt: the first harness start had no readable session token on my side, so I killed it, deleted that config and restarted; the numbers below are from the second Core only.

## 3. Refusals

### (a) Valid token, no grants

- `claude mcp list` (HTTP, no-grant token): `phoenix: http://127.0.0.1:48932/mcp (HTTP) - ✔ Connected`; stdio: `✔ Connected`. Gemini (below): `✓ ... Connected`. A connection check does not need a grant; the client then lists **zero tools** (`tools/list` -> `{"tools":[]}`, seen on the proxy).
- A tool **call** cannot be issued by `claude mcp ...` or `gemini mcp ...` without a model, so **no real client was refused on a tool call**. What the real clients show: they got an empty tool list, so no tool could even be offered to a model.
- NOT A REAL CLIENT (curl, labelled as such): `tools/call` of `phoenix_activity`, `phoenix_notify` and `phoenix_request_approval` with the no-grant token returned `{"jsonrpc":"2.0","id":..,"error":{"code":-32602,"message":"Unknown tool"}}`; the same call with the granted token returned `{"result":{"content":[... "{\"untrusted_data\":[]}"]}}`. The Core audit shows 3 `mcp.call.denied` rows with reason `not_granted` for the no-grant client and one `mcp.call` for the granted one.

### (b) Wrong token (the granted token plus one extra character)

- Claude Code HTTP: `phoenix: http://127.0.0.1:48932/mcp (HTTP) - ✘ Failed to connect — Server rejected the configured Authorization header (HTTP 401). Check that the token is valid for this MCP endpoint — OAuth fallback is disabled when headers.Authorization is set. Error detail: {"jsonrpc":"2.0","id":null,"error":{"code":-32600,"message":"Invalid or revoked token"}}`. `claude mcp get` shows `Status: ✘ Failed to connect` with the same text. Not "needs auth": Claude Code treats the explicit header as final (no OAuth fallback).
- Gemini HTTP: `✗ phoenix: http://127.0.0.1:48932/mcp (http) - Disconnected` (one `initialize`, 401).
- Core side: `mcp:unknown mcp.call.denied bad_token` rows (12 over the whole session; an unknown token has no client to attribute to, so rows share the `unknown` actor).
- **Defect found and fixed: stdio bridge, wrong token, Claude Code.** Before the fix `claude mcp list` printed `✘ Failed to connect — MCP server "phoenix" connection timed out after 30000ms` (command took 35 s). Cause: the server answers a pre-parse refusal (401) with `"id": null`; the bridge relayed that verbatim, Claude Code matches replies by id and waited for its `initialize` (id 0) until its 30 s timeout. After the fix the bridge gives the error the request's id and the same real client prints `✘ Failed to connect — -32600: Invalid or revoked token` in 0.7 s. Gemini stdio, wrong token, after the fix: `✗ phoenix ... (stdio) - Disconnected`.

## 6. Snippet checks and doc changes

- Claude Code HTTP snippet: correct as written. Claude Code accepted it, `claude mcp add` redacted the header, but `claude mcp get` prints the header with the token in clear.
- Claude Code stdio snippet: correct as written. If Phoenix is not on 47822 the bridge also needs `PHOENIX_MCP_URL`. Without it (shell has only `PHOENIX_MCP_TOKEN`, Core on 48931) `claude mcp list` printed `✘ Failed to connect — -32603: Phoenix is not reachable` (0.6 s). With `--env PHOENIX_MCP_URL=http://127.0.0.1:48931/mcp` added to the `claude mcp add` it printed `✔ Connected`.
- The doc said "Never put it [the token] on a command line". Both the HTTP snippet (`--header "Authorization: Bearer $PHOENIX_MCP_TOKEN"`) and Gemini's `-e`/`-H` do put the expanded token on the arguments of the short-lived `add` process, and every client writes it into its own config file in clear. Documented.
- docs/mcp-server.md was changed: status block, the Claude Code section (verified, with the observed handshake), a new Gemini CLI section, Cursor/Codex still marked unverified (not installed), the token-on-argv note, the real-client handshake table, and the "What is and is not verified" rows.
- Code change (only the obvious defect): `scripts/mcp/phoenix-mcp-stdio.mjs` now copies the request id into a server error reply whose id is `null`. Test `core/runtime/test/mcp-stdio-bridge.test.ts` ("answers a refusal the server raised before it read the request with the request's own id") FAILED before the change (`"id": 0` expected, got `"id": null`) and passes after: `node ./node_modules/vitest/vitest.mjs run core/runtime/test/mcp-stdio-bridge.test.ts --testTimeout=60000` -> 11 passed.
