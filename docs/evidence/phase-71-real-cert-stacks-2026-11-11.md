# Phase 71: the phone listener's certificate on independent desktop TLS/X.509 stacks (2026-11-11)

Raw data: [`phase-71-real-cert-stacks-2026-11-11-raw.json`](phase-71-real-cert-stacks-2026-11-11-raw.json) (one run of the gated test, plus the hand-run controls listed under "LibreSSL").
Produced by `core/runtime/test/real-phone-cert-stacks.test.ts` with the probes in `core/runtime/test/real-cert-stacks/` (`probe.swift`, `probe.go`, `Probe.java`, `probe.py`).

**What this is.** The REAL phone TLS listener (production `PhoneLink` + `PhoneListener` + `ensureTlsIdentity`, started by `startCore` with only the LAN address list set to `127.0.0.1` and the port set to 0) was reached over loopback by seven independent desktop stacks on **macOS 27.0.1 (26A434), arm64**. Nothing was installed and nothing left loopback.

**What this is not.** No iOS device, no Android device, no iOS Simulator, no Android emulator. Apple's Security framework and `URLSession` on macOS are the same family as on iOS, but iOS's Network.framework policies were not exercised, and Android's BoringSSL/Conscrypt and its Network Security Config were not exercised at all. Nothing here closes the Phase 71 exit criterion. The certificate's address is `127.0.0.1` because the test used loopback; the 192.168/10/172.16 LAN case uses the same code path with another 4-byte IP SAN and was not run.

## Results: strictness checks phones apply

- **Validity length.** 90.0035 days. This is inside Apple's 825-day (2019) and 398-day (Sept 2020) limits for certificates chained to **trusted** roots, so the certificate would satisfy the 398-day rule too. [INFERENCE, from Apple's published policy, not tested here] Those limits apply to server certificates chained to roots in the system store. A pinned, self-signed certificate is not in that class; I did not run a test that proves exactly how iOS treats a long-lived self-signed leaf, so no claim is made there. What macOS's `SecTrust` did say: with the certificate as the only anchor and the SSL policy for `127.0.0.1`, **trusted** (no error, no warning); with a wrong hostname, `certificate name does not match input` (-67602); with another certificate as anchor, `not trusted` (-67843); with the evaluation date 400 days ahead, `certificate is expired` (-67818).
- **SAN.** An IP SAN (iPAddress, 4 bytes) is present, with no DNS names. Apple, Go, Java, Python/OpenSSL 3.6 and OpenSSL 4.1 each matched the IP host against it in the trust-anchor handshakes (the `-verify_ip`/`check_hostname`/`ServerName` rows above, and OpenSSL 4.1 `x509 -checkip 127.0.0.1`: `IP 127.0.0.1 does match certificate`). The subject CN holds no address, so a client that ignores SAN and matches CN would not match; this was not exercised (each tested stack matched the IP SAN). The LAN address in a real deployment was not tested; only 127.0.0.1.
- **Serial.** Positive, at most 127 bits (16 bytes with the top bit clear), within RFC 5280's 20-octet limit. All stacks agreed it is positive.
- **keyUsage and EKU.** digitalSignature only, critical, and serverAuth, as ECDSA ECDHE suites need. No stack required keyEncipherment.
- **Self-signed, CA:FALSE.** Apple, Go, Java, Python/OpenSSL 3.6 and OpenSSL 4.1 accepted the certificate as its own trust anchor.

## The one stack that did not accept it as its own anchor: LibreSSL 3.3.6

`/usr/bin/openssl verify -CAfile served.crt served.crt` and `s_client -CAfile served.crt -verify_return_error` both fail with `error 20 at 0 depth lookup: unable to get local issuer certificate`, with or without `-purpose sslserver` or `-x509_strict`. OpenSSL 4.1.0 says OK for the same command. Hand-run controls (raw JSON, key `manualControls`; certificates generated with OpenSSL 4.1.0 and deleted): the same profile fails in LibreSSL 3.3.6; the same profile with `keyCertSign` added, or with no `keyUsage` extension, or with `CA:TRUE`, passes. So LibreSSL 3.3.6's older verifier will not treat a self-issued certificate whose keyUsage lacks `keyCertSign` as its own issuer. This is an issuer-lookup rule of that old chain builder, not an encoding defect: the same bytes parse cleanly in all six parsers, and fingerprint pinning (the model Phoenix specifies, which never builds a chain) completed against LibreSSL. It matters only for a client that verifies by loading this certificate as a CA root in an old LibreSSL-class verifier. The builder was NOT changed: adding `keyCertSign` or `CA:TRUE` would make a leaf look like a CA to every other stack, for a client the pinning design does not use. Recorded as a limitation, not fixed.
