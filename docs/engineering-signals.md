# Engineering signals

EngineeringSignals reads only explicitly configured absolute, non-symlinked repository roots. No recursive discovery occurs. Manual `scan()` is read-only and works without notification opt-in; scheduled `evaluate()` requires explicit Phase 52 opt-in. `setWatchedRoots` replaces the complete watch list and `stop` cancels its timer. A repository removed from the watch list no longer produces findings. The collector reads top-level `package.json`, `Cargo.lock`, `requirements.txt`, `go.mod`, `.env.example` and `.env`, plus history supplied by an injected terminal/CI history source. It never runs build commands or contacts an advisory service. The injected advisory provider receives exact pinned dependencies, not arbitrary package ranges; returned advisories must match the inventory. Configure a provider backed by an approved read-only service before enabling advisory checks.

Flakiness requires both a pass and failure among at least three recent runs of the same source/job/test identity. A duration increase requires six recent runs, compares medians of consecutive sets of three, and reports at least a 50% and 1000 ms increase. Histories beyond 30 days are excluded. `.env` is read as a line stream containing only parsed assignment names; neither configuration values nor command output are included in a signal. Missing `.env` is not treated as proof of drift. Symlinked env files are refused.

To integrate, export `@phoenix/ai-proactive/engineering` from the package manifest to `./src/engineering/index.ts`. Instantiate `EngineeringSignals` with injected `AdvisoryProvider.lookup(dependencies)`, `HistorySource.list(root)`, `Clock.now()`, `Timer.set/clear`, `Delivery`, and a cadence of at least 60 seconds. `createEngineeringDelivery({notifications, userId, killSwitchEngaged, capabilityEnabled})` supplies the Phase 52 delivery adapter: `notifications` needs `proactivePreferences(userId)` and `considerInsight(userId, insight, isCurrent)`. The adapter requires persisted enabled/cadence and `engineering-signals` capability consent plus an active capability and disengaged kill switch. NotificationService retains authority for timezone quiet hours, deduplication and hourly noise limit. Extend `ProactiveInsight.kind` with all four engineering signal kinds, rather than relabeling them as dependency updates. Call delivery synchronously with the current-evidence callback (which expires on the next scan, revoked root or consent change). Persist only explicitly user-approved watched roots in existing settings storage. Schedule at the user's chosen cadence, stop on revocation and shutdown, and expose GET `/api/engineering-signals` and PUT `/api/engineering-signals/watched-roots` with `{ watchedRoots: string[], signals: EngineeringSignal[] }` for the web dashboard. Core now serves both routes: GET is a manual read-only scan that also returns provider availability, and PUT takes `{ watchedRoots }` and stores the roots under the settings key `engineering-signals.watched-roots` (listed in the privacy inventory as `engineering_signals_roots`). The scheduler starts with Core and runs only while the `engineering-signals` capability id is opted in with a cadence set in the proactive preferences and the kill switch is off; it stops on opt-out or when the kill switch engages. Core's `capabilityEnabled` is hard-wired to true (there is no capability manifest), so the opt-in is the only gate. The web `ProactiveSettings` writes only `["kage"]` or `[]`, so no screen can opt in to `engineering-signals` today (and saving that form clears an engineering opt-in); the `EngineeringSignals` panel in Settings shows an unavailable-provider notice instead of "no signals".

Limitations: the advisory provider is always unavailable in production (no approved local advisory database exists and nothing contacts the network), so advisory signals never fire there. The history provider reads only the last 1000 terminal events, so only job-level duration trends can come from it; flaky-test and CI signals cannot fire from it. Terminal events can be forged by any session-token holder (the `terminal` source is not reserved on `POST /api/events`). Temp-fixture tests do not establish findings from real user repositories. No advisory is emitted from unresolved npm ranges or unpinned pip requirements.
