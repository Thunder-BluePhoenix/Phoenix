# Service terms and rate limits read for the pollers

**This is NOT legal advice and NOT a terms-compliance review.** It records what the public documentation
pages listed below said on **2026-11-10**, as read by an automated tool (not a lawyer), and the poll
defaults Phoenix derived from those pages. Pages change; limits "may change without notice" (Solana,
Notion, TronGrid say so themselves). Where a page was unreachable, rendered only with JavaScript, sat
behind a bot challenge, or was ambiguous, that is said and the existing default was kept. Nobody has
run these pollers against the real services (see `docs/gaps.md`, rows 67 and 68).

Phoenix is a personal, read-only desktop poller: one user, one machine, one IP, GET requests (plus one
read-only JSON-RPC POST for Solana balances) on the user's own accounts and addresses, started only while
something is watching Phoenix (`ctx.untilWatched`). A reading of "terms of use" for _commercial_ or
_redistributing_ use is out of scope, but where a page states a licence constraint it is quoted below
because it matters if the user ever shares the output.

## How the defaults are enforced in code

- Every capability has `DEFAULT_POLL_MS` and `MIN_POLL_MS` (the schema `minimum`, applied with
  `Math.max`). A test per capability (`test/service-limits.test.ts`) recomputes the request rate the
  defaults and floors produce from the documented limit in this file and fails if either goes below it.
  The documented numbers live in each capability's `src/limits.ts` (or beside the constant) with the URL
  and the date read.
- `429` honours `Retry-After` (`nextDelay` in `sdk/service-kit/src/poller.ts`, capped at one hour);
  `401` waits at least five minutes; failures double the delay up to five minutes. Unchanged.
- Portfolio networks with a documented hourly or daily budget carry `budget` in `networks.ts`; the poll
  delay is raised so the requests of one cycle never exceed it (see Portfolio below).

### Stripe note (raised defaults)

The Stripe page says every account has "a minimum allocation of 10,000 read requests per month" and a
transaction-based allocation above that. 10,000 reads over a 30-day month is one read per 259 s. Phoenix's
Stripe poller makes the charge list call each cycle (and the balance call on status requests, not per
cycle; see `capabilities/stripe/src/index.ts`). A default of 60 s would spend about 43,000 reads a month
and is not inside the minimum allocation for a low-volume account. The default is therefore 600 s (about
4,300 reads a month) and the floor 300 s (about 8,600 reads a month, inside 10,000). An owner with many
transactions has a larger allocation and can lower the interval only down to the floor; going below it
needs a code change on purpose.

## What this does not establish

- Nothing here was checked against live responses.
- Terms pages for Vercel, Resend, Cal.com were fetched and searched by keyword, not read in full; Notion,
  n8n, Blockstream, BlockCypher, Stellar, Nodely usage policy, PublicNode, CoinGecko, OKX, KuCoin, Gate and
  Coinbase terms were not read.
- A reading of "documented limit" is not permission: a vendor may refuse automated polling of an unpaid
  tier for reasons not on these pages.
