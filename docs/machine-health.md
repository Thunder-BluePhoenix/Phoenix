# Machine health and local models

Enable the `machine` capability and mount `MachineHealth` from `apps/web/src/components/MachineHealth.tsx` in the web app. Register `createMachineCapability()` from `@phoenix/capability-machine` in the runtime builtins, add the workspace package to the root manifest and lockfile, and wire the `machine` namespace in the English and nine locale indexes. The standard capability command gateway handles permissions, confirmations and audit records. No migration or new service route is required.

`health_snapshot` reads disk free/total, available memory, CPU load, battery and temperature. Missing/unreliable measurements remain null; CPU on Unix is normalized load average, not instantaneous utilization. The Windows reader uses PowerShell/CIM for CPU and battery. macOS and Windows do not provide a reliable portable unprivileged thermal probe, so temperature remains unavailable there. Linux uses the first standard thermal zone; on devices with another zone this is only an indicative reading. Warnings emit a `machine.health.warning` event, grouped by metric into Fawkes WARNING, and recovery clears it. Thresholds: disk below 10 GiB or 10%, free memory below 2 GiB, CPU at least 90%, unplugged battery at most 15%, reported temperature at least 85 °C. Measurements are on demand, not continuous monitoring.

`list_models`, `download_model`, `remove_model`, `run_model`, `check_fit` and `suggest_cleanup` accept only Ollama or LM Studio. The HTTP client uses fixed `127.0.0.1` origins (ports 11434 and 1234), fixed endpoint paths and refuses redirects. No caller-supplied host or URL is accepted. The manager reads Ollama `/api/tags` and `/api/ps`, LM Studio `/api/v1/models`; downloads via Ollama `/api/pull` (non-streaming) or LM Studio `/api/v1/models/download`, loads via Ollama `/api/generate` or LM Studio `/api/v1/models/load`; Ollama removal uses `/api/delete` only for a freshly listed installed model. LM Studio's documented REST API has **no deletion endpoint**; Phoenix refuses removal and directs users to LM Studio instead. The suggestions only identify installed unloaded models for user approval; caches and arbitrary files are never deleted. Removal, downloads and runs all require separate capability gateway confirmation.

**Verified-size prerequisite:** Neither provider's documented local API exposes a trusted size for a model _before it is first downloaded_. A user-supplied estimate is insufficient for a safety decision. By default, `check_fit` and `download_model` refuse all new downloads. An embedding with a trusted catalog can inject `catalogSize(provider, name): Promise<number | null>` into `createMachineCapability`; the size is rechecked against free disk (model × 1.25 + 2 GiB reserve) and free memory (model × 1.25) immediately before calling the provider. Unknown free space/memory also fails closed. **In production no catalog is injected** (`core/runtime/src/builtins.ts` passes none), so `check_fit` and `download_model` refuse with "Verified model size unavailable"; list, run, remove and health work. The phase's "a model is downloaded and removed through Phoenix" exit criterion is unmet; fake-catalog tests cover the download lifecycle without contacting providers, and no real Ollama or LM Studio was exercised through Phoenix.
