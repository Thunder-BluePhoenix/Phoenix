# Calendar awareness and meeting preparation

The read-only calendar capability reads Google Calendar, Microsoft Graph and CalDAV through adapters that Core builds from the capability's own config and secrets when the feed is read (see "Connecting a calendar" below); macOS Calendar needs a host-supplied reader that this repository does not contain. Importing or enabling the capability contacts no provider until one is switched on. Calendar content is untrusted data, not instructions. Private events expose only a busy placeholder. Five-minute reminders are issued once per occurrence and start time, and that fact survives a Core restart (see "Reminder de-duplication" below).

Meeting preparation finds previous related meetings and reviewed decisions and open action items. The runtime query (`StoreMeetingPrepQuery`) reads accepted reviewed items of prior meetings with matching participants and is gated on `allow_sensitive_meetings`; project-only matching returns nothing because meetings carry no project field. No transcript is fetched for this feature. The notetaker button only navigates to `#/meetings`; it never starts a recording. A reminder becomes a notification ("A meeting is starting soon") through the always-notify list in `core/notifications`; it is never stored as a durable event.

A deploy freeze applies only when the user enables the calendar `freeze` setting (default false). When it is on, the `CapabilityManager` `preflight` hook runs after approval and before dispatch and refuses commands with side effect `production` and `vercel/redeploy` unless a fresh feed shows no freeze window; it fails closed (`SECURITY_POLICY_BLOCKED`) when the feed is missing, stale, unreadable or incomplete, or a credential is missing. With the freeze on and no provider configured (or a configured one failing, for example an expired Google or Graph token), every such command is blocked, because the feed is not a clean, fresh one. Not covered: agent permission-request approvals (AgentApprovals) and other external side effects (n8n, terminal).

All present test evidence uses injected fake providers, loopback fake servers and store records; no live account, real calendar server or real token has been used. Phase 83's exit criterion, **a real calendar event triggering a reminder and a prep note**, remains unmet until one real account is read end to end.

The feed fails closed. A configured provider with a missing credential, a failed or paginated read, truncation, or any unreadable event makes the whole feed unavailable; Core reports `status` as `unavailable` or `stale` and the page says so rather than "No upcoming meetings". The freeze snapshot always requests a fresh read. A blocked deploy raises `PhoenixError(SECURITY_POLICY_BLOCKED)`. Freeze markers are listed in `capabilities/calendar/README.md`.

## Reminder de-duplication

A reminder is keyed by a SHA-256 digest (first 32 hex characters) of the occurrence id and its start time, so a rescheduled meeting is reminded again but a restart is not. Core lends the capability one settings key, `calendar.reminders.sent` (`core/runtime/src/calendar/reminder-store.ts`, passed through `builtinCapabilities(..., { calendarReminders })` and wired in `main.ts`), holding `{ "version": 1, "sent": [{ "key", "start" }] }`: the opaque key and the start time in epoch milliseconds, never a title, id, attendee or link. Records are dropped once the start time has passed, and at most 500 are kept (latest starts win). Stored data is untrusted: anything that is not that exact shape, including unparseable JSON, malformed entries and a record dated further ahead than the five-minute window, is ignored.

If the store cannot be read or written, the reminder is still sent once (a missed meeting reminder is worse than a repeated one) and nothing is logged, because nothing in that path may carry event content; the in-memory record still prevents repeats in the running process. Without a `reminderStore` option (tests, other hosts) de-duplication is in memory only. Tests: `core/runtime/test/calendar-reminders-restart.test.ts` (a real `PhoenixRuntime` restarted on the same SQLite file) and the "persisted reminder keys" cases in `capabilities/calendar/test/calendar.test.ts`. Both are simulated evidence with a fake calendar.

## Connecting a calendar

`createCalendarCapability()` is called with no adapters in `core/runtime/src/builtins.ts`; the adapters are built from config and secrets on each read. Nothing is configured by default, and until a provider is switched on the feed is `unconfigured` and no network request is made. Secrets are write-only (`POST /api/capabilities/calendar/secrets/<name>`), live in the OS keychain, are refused in config, and never appear in events, errors, `upcoming` results, logs or the privacy inventory (which lists a stored secret by name only). Config is read when the capability starts, so disable and enable it after changing settings.

| Provider        | Config                                                                    | Secret                                                            | Sent to                                               |
| --------------- | ------------------------------------------------------------------------- | ----------------------------------------------------------------- | ----------------------------------------------------- |
| CalDAV          | `caldav: true`, `caldav_url` (one collection), optional `caldav_timezone` | `caldav_credential` = `username:password` (an app password)       | only the host in `caldav_url`, HTTP Basic             |
| Google          | `google: true`                                                            | `google_credential` = an OAuth access token (`calendar.readonly`) | `www.googleapis.com`, Bearer                          |
| Microsoft Graph | `microsoft: true`                                                         | `microsoft_credential` = a Graph access token (`Calendars.Read`)  | `graph.microsoft.com`, Bearer                         |
| macOS           | `macos: true`                                                             | none                                                              | no reader in this build: the feed reports unavailable |

Rules for every network provider: https only (plain http only to localhost), no credentials, query or fragment in `caldav_url`, GET (CalDAV: one read-only `REPORT`) only, **redirects are refused** so a credential never travels to another host, a 15 second deadline covering the whole body, and a 2 MiB cap on the answer. Validation errors are fixed phrases that never echo the address, the credential or text from the server. The `upcoming` result shows `sends_caldav_credential_to` (the CalDAV host).

Limits stated plainly:

- **No OAuth flow.** Phoenix does not obtain or refresh Google or Microsoft tokens. The owner pastes an access token (valid roughly one hour); when it expires the feed becomes `unavailable` (the 401 message says the credential is invalid or expired) until a new token is stored. That makes Google and Graph a poor fit for an always-on feed until a real OAuth flow exists, which needs an owner decision (client registration, redirect handling, refresh-token storage).
- **`caldav_url` is a config setting.** Whoever can change config can point the stored CalDAV login at another host. Phoenix shows the host and cannot prevent the change; this is the same open owner decision as n8n's `base_url`.
- CalDAV events are expanded by the server (`<C:expand>`); an event that still has `RRULE`/`RDATE` fails the feed rather than guessing occurrences. `VTIMEZONE` blocks are ignored: only IANA `TZID` names are read, and an unknown zone fails the feed.
- Project-only prep matching stays empty on purpose: meetings carry no project field (the `meetings` table has none; `project_ref` items are extracted topics and are not reviewable, so they are not an authorized match). Inventing one from a title would be an unauthorized match. Decision for the owner: add an explicit project association on meetings before prep may match on it.

Tests: `capabilities/calendar/test/providers.test.ts` (loopback fake CalDAV, Google and Graph servers; fake adapters for the injected path) and `core/runtime/test/calendar-caldav.test.ts` (a real Core through the HTTP API). Simulated evidence only.
