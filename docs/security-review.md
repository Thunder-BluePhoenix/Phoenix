# Security review — v0.1

Walks the threat model in the Full System PRD v2.0 §18 against the code as it stands. Each row names the mitigation, where it lives, and the test that would fail if it broke. A mitigation with no such test is marked **no automated proof**. Nothing here was reviewed by anyone outside the project.

Scope: Phoenix Core, the web app, the built-in capabilities (Kage, Git, terminal, mock) and the macOS desktop shell. The Linux and Windows desktop shells have not been built.

## Found and fixed during this review

- **Core could be crashed by one unauthenticated-looking event.** A meeting-shaped event from a source that is not a registered capability (for example `source: "ghost"` posted to `/api/events`) made the meeting sync throw `Capability "ghost" not found` outside any handler. Node treated that as an unhandled rejection and the process exited. A real Core was confirmed to die this way. The lookup is now inside the handler, and `meetings.test.ts` "do not crash core" fails without the fix. Anyone who holds the session token could trigger it, so the impact is a local denial of service against a process that already trusts that token.
- **A registered external capability could forge Phoenix's own events.** The manifest's `events` list only had to be well-formed, so a capability could declare `["security.*"]` and publish `security.confirmation.requested`. Fawkes went to WAITING with "Approval needed: Click approve to continue" while Core had no pending approval (`pendingConfirmations()` was 0). It could also publish `capability.failed` for Kage, which put Fawkes in ERROR and created notifications. Manifests that declare an event in a reserved namespace (`core`, `pet`, `system`, `security`, `phoenix`, `fawkes`, `capability`, `notification`) are now rejected with 400. Tests: `manifest.test.ts` "rejects events in a namespace Phoenix reserves for itself" and `api.test.ts` "external: cannot register to speak as Phoenix…" (both fail without the fix). The rule lives in manifest validation, which built-in (in-process) modules go through as well (`manager.test.ts` "applies the reserved-namespace rule to in-process modules too"); it is a registration-time check, so it does not look at what a module actually publishes.
- **A registered external capability could make Core buffer an unlimited reply.** A 200 MB streamed `/health` reply took Core's memory from 129 MB to 987 MB, because the whole body was read and the timeout covered only the headers. Replies are now capped at 1 MiB (`MAX_RESPONSE_BYTES`), the connection is dropped at the cap, and the whole read has to finish within the request timeout (a body that stalls after its headers used to wait forever). Health `message` text is cut to 300 characters. Tests: `external.test.ts` (4 of 5 fail without the fix).
- **The mock Kage server made every test that used it wait about 3 s on teardown** (kept-alive connections). Not a security issue; fixed because it made the new diagnostics tests slow.

## Known gaps

These are real and are not fixed in v0.1.

1. **The session token is the only credential.** Anything running as the same user can read `session.token` and call the API. That is the stated model (ADR-0015), but it means Phoenix does not protect the user from their own malware.
2. **No sandbox for capabilities.** Built-in capabilities run inside the Core process. A bug in one can read anything Core can.
3. **Unregistered sources can still write to history.** `POST /api/events` accepts a well-formed event from any `source` other than `core`, with the session token. Such events appear in the activity feed and can change Fawkes's state. They cannot start a recording or run a command, but a holder of the token can make Fawkes show "Meeting processing failed". This is the same trust boundary as gap 1: the token holder is trusted. The reserved-namespace rule above only constrains _registered_ capabilities, which hold a different, narrower token. Registering sources would close this; it is a design change, not a fix.
4. **Meeting records created by an injected event** (see above) show up in the Meetings list with whatever title the sender chose. They have no transcript or summary. Same cause, same remedy as item 3.
5. **Start on login registers the binary that is running.** A debug build registers the debug binary. Packaged builds have not been checked.
6. **Windows has no OS secret storage** (`KeychainSecretStore` supports macOS and Linux). On Windows Core cannot store capability credentials.
7. **Dependency scan covers what is on disk, not what ships.** `pnpm audit` and `cargo audit` ran clean on 2026-10-08 and now run in CI. They check the lockfiles against known advisories only, so an undisclosed flaw or a malicious release is not caught. Two `cargo audit` warnings (unmaintained `proc-macro-error`, unsound `glib 0.18`) are in the Linux GTK stack and are not in the macOS build; they must be revisited before a Linux build ships. Dev tooling was upgraded (Vitest 3 → 4.1.11) to clear two critical and two moderate advisories in the test runner.
8. **The desktop window's Content-Security-Policy allows `http://127.0.0.1:*`** so it can reach Core on any port. It cannot reach other hosts.
9. **Diagnostics redaction is a safety net, not the design.** The report is built from an allow-list; `redact()` runs over the result only to catch secret-shaped text. A new field added carelessly would still leak, which is why the test seeds real content and checks for it.
10. **Sensitive data can reach a cloud AI, by the user's choice.** The Phase 29 opt-in (`cloud_opt_in.sensitive`) exists on purpose: with the external-processing grant on and that box ticked, sensitive memories (including meeting summaries) are sent to the cloud provider when the user asks Fawkes a question, or whenever the user has set that provider as preferred. It is off by default, needs its own explicit confirm in the UI, and every send is audited by counts. It is a deliberate user decision, not a defect; the provider then holds that text under its own terms, and Phoenix cannot recall it. Secret-shaped text is redacted before storage, but ordinary sensitive prose is sent as it is.
11. **Memory has no multi-user model.** Core runs every memory route as the device owner (`ownerViewer`); `canView` is applied everywhere, but the only viewer Core builds today sees everything. The permission model is proven with narrower viewers in tests (`RuntimeOptions.memoryViewer`), not by a second user in a real deployment.
12. **The Anthropic key is read from the OS secret store on every cloud request** and is held in memory only for that call. Core cannot tell the user which key it holds, only that one is set; `GET /api/ai/status` reports a missing key as the provider being unavailable.
