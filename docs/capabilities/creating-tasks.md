# Creating GitHub issues, Linear and Jira issues, and Frappe tasks

Six capability commands write to the outside world. All are **opt-in twice** (a write credential you set yourself, and a confirmation you give for every call) and none has ever been run against a real GitHub repository, Linear workspace, Jira Cloud site or Frappe site; they were exercised only against local mock servers or a fake `fetch`.

## GitHub: `github.issue.create`

1. Create a fine-grained token with **Issues: read and write** on the repository you want, and store it as the `write_token` secret of the `github` capability (`POST /api/capabilities/github/secrets/write_token`). The read `token` used for watching is never used to write, and `write_token` is never used for watching. Without `write_token`, the command fails before sending anything.
2. Input: `{ repository, title, body?, labels?, idempotency_key }`. Always confirmed, side effect `external`.
3. The body ends with a hidden `<!-- phoenix-ref:KEY -->`. Repeating a call with the same key returns the existing issue (`status: "existing"`). GitHub search is eventually consistent, so a retry made long after, but before the search index catches up, can create a duplicate.

## Frappe: `frappe.task.create`

1. Create an API key and secret for a user that may create `Task` documents and store `api_key:api_secret` as the `write_token` secret of the `frappe` capability.
2. Tell Phoenix where to write: capability config `api` maps a site name to a base URL, for example `{"api": {"erp.localhost": "http://127.0.0.1:8000"}}` (https anywhere; http only for loopback). The write URL is never taken from your bench files or from the health-check `sites` overrides.
3. Input: `{ site, subject, description?, priority?, exp_end_date?, project?, idempotency_key }`. The description ends with a visible `Phoenix ref: KEY` line; a repeat with the same key finds the Task instead of creating another.

## Linear and Jira: `issues` capability (Phase 85)

Two more commands of the `issues` capability, `linear.issue.create` and `jira.issue.create`. Polling stays read-only; these and the two attach commands below are the only writes. **The create commands are text only: no image, file or attachment is sent by them.** An image can be attached afterwards with the separate, separately confirmed `jira.issue.attach` and `linear.issue.attach` (next section).

1. Credentials are write-only secrets of the `issues` capability and separate from the polling ones (a polling key never enables writes; a missing write credential fails before any request): `linear_write_key` (Linear personal API key), or `jira_write_email` plus `jira_write_token` (Atlassian API token). They are never returned, logged, put in an error or audit row.
2. Linear: input `{ team_id, title, body? }` (`team_id` is the team's UUID). The request is one fixed GraphQL `issueCreate` mutation with the input as variables, always to `https://api.linear.app/graphql`; the polling `api_url` override does not apply.
3. Jira Cloud: set capability config `create.jira_site` to your site, `https://<name>.atlassian.net` (https and `*.atlassian.net` only; the configuration is rejected otherwise, and the client checks again). Input `{ project, title, body?, issue_type? }` (`issue_type` defaults to `Task`; `project` is the project key such as `PROJ`). The call is `POST <site>/rest/api/3/issue`; the description is sent as a plain Atlassian Document Format document of text and line breaks. The input cannot name a host.
4. Both are `external` commands: Core asks for confirmation on every call and the card shows the destination (team or project), title and the start of the description (control and format characters removed). Core's audit log records the confirmation request, the decision, the authorisation and the outcome; it holds the command name and a redacted summary, never a credential or the tracker's reply text.
5. Title (1 to 255 characters) and body (up to 10,000) are secret-redacted and stripped of control and format characters before sending. Redirects are refused, there is a 15 s timeout and a 256 KiB reply cap. The result is only `{ tracker, id, key, url }`: the Linear url must be an `https://linear.app/<workspace>/issue/<KEY>` link for that exact key, and the Jira url is built from the pinned site and the validated key, never taken from the reply. Errors are fixed text; after the request was sent, a timeout, a dropped connection, a redirect, an HTML or oversized reply or a 5xx says the issue may or may not exist.
6. **No idempotency key.** Neither tracker offers the cheap lookup GitHub's marker relies on, so repeating a call after an unknown outcome can create a second issue; look in the tracker first.

Evidence: `capabilities/issues/test/create.test.ts` runs both commands against a fake `fetch` only. No real Linear workspace, Jira site, account, key or token was contacted, and the request and reply shapes come from the vendors' documentation, not live responses.

## Attaching a screenshot: `jira.issue.attach` and `linear.issue.attach` (Phase 85)

Two more `external` commands of `issues`, one per tracker, so Core confirms every call and the card says which tracker. They attach **one PNG to an issue that already exists**. GitHub has **no** attach command: GitHub offers no documented REST endpoint for uploading an image to an issue (the web UI's own upload endpoints are undocumented), and Phoenix does not use undocumented endpoints, so GitHub issues stay text only.

- **Input.** `{ issue, image_base64, bytes, sha256_prefix, file_name }` and nothing else (extra fields are refused). `issue` is the key (`PROJ-7`, `ENG-12`). The image must be a whole PNG: signature, a 13-byte IHDR first, width and height 1 to 16,384, IEND last, at most 5 MiB (the same `inspectPng` the capture adapter uses). JPEG, a path or a URL is refused before any request.
- **File name is generated, never taken from input.** It is `phoenix-screenshot-<first 12 hex of SHA-256>.png`. `file_name`, `bytes` and `sha256_prefix` are in the input only so Core's approval card can show them (`x-phoenix-confirm`: the card shows the issue key, file name, byte size and hash prefix). The capability recomputes all three from the decoded bytes and refuses the call, before any request, if any differs, so the card cannot describe a different file than the one sent. The image itself cannot be rendered in a card; the hash and size bind the card to the bytes.
- **Credentials and hosts.** The same write-only secrets as the create commands (`jira_write_email` + `jira_write_token`, or `linear_write_key`); polling credentials are never used. Jira is pinned to the owner-set `*.atlassian.net` `config.create.jira_site`; Linear to `https://api.linear.app/graphql`.
- **Jira.** `POST <site>/rest/api/3/issue/{key}/attachments`, `multipart/form-data` with one part named `file` (content type `image/png`) and the header `X-Atlassian-Token: no-check`, as in Atlassian's "Add attachment" reference. The reply must be a one-entry array with a numeric id; its other text is never shown.
- **Linear.** Four requests, from Linear's "How to upload a file to Linear" guide: (1) look the issue up by key and require the same identifier back; (2) the `fileUpload` GraphQL mutation (content type, file name, size), which returns a signed `uploadUrl`, `assetUrl` and the `headers` the upload needs; (3) a `PUT` of the bytes to the signed URL with those headers; (4) `attachmentCreate` linking the `assetUrl` to the issue. The signed URL is accepted only if it is `https`, has no credentials, port or fragment, no dot segments or encoded slashes, is at most 4096 characters, and its host is `storage.googleapis.com` or a single-label `<bucket>.storage.googleapis.com` (Linear's SDK documents the upload as going to Google Cloud Storage by signed URL; Linear's own text does not name a host, so this allow-list is Phoenix's justified reading, and an upload address elsewhere is refused with nothing sent). The `assetUrl` must be `https://uploads.linear.app/<plain path>`. Only `Content-Type: image/png`, `Cache-Control`, `Content-Disposition`, `Content-MD5` and `x-goog-*` headers from Linear's reply are forwarded; anything else (an `Authorization`, `Host`, `Cookie`) refuses the call. **Phoenix's Linear key is never sent to the storage host.** The signed URL is used for the one `PUT` and is never logged, returned, put in an error or audit row.
- **Limits.** No redirects (a 3xx is refused and the error says the outcome is unknown), 30 s per upload request (15 s per Linear JSON request), replies capped at 256 KiB, fixed secret-free errors that never hold anything the remote side wrote. No idempotency key: a retry after an unknown outcome can attach the image twice; look in the tracker first. If the upload succeeded but the final link request failed, the error says so (the file then sits in Linear's storage, unlinked).
- **Body size.** The image travels inside the command input, so Core's API grants these two command paths (and no other) a 7 MiB request body instead of 256 KiB (`ISSUE_ATTACH_BODY_MAX_BYTES`). The input is held in Core's in-memory operation record like any command input.
- **In the app.** The screenshot flow creates the Linear or Jira issue as text, then, only if you choose "Show what would be attached", ticks a second confirmation and presses "Request approval and attach", Core asks again. See [focus and screenshot](../focus-and-screenshot.md).

Evidence: `capabilities/issues/test/attach.test.ts` (fake `fetch` only: multipart body shape, the no-check header, host pinning, a signed-URL validation table, hostile replies, secrets and the signed URL never in an output) and `core/runtime/test/issue-attach-wiring.test.ts` (real Core: the larger body limit on exactly those two paths). **No real Jira site, Linear workspace, Google Cloud Storage bucket, account, key or token was contacted**; every request and reply shape comes from the vendors' documentation, and nothing was observed live. Whether Linear's real upload host fits the allow-list, whether a real `fileUpload` returns exactly the documented headers, and Jira's real per-site attachment limit (`/rest/api/3/attachment/meta` reports `uploadLimit`, which Phoenix does not read) are unverified.

## All of them

- A redirect from the server is refused. Responses are size-capped. Titles and bodies are secret-redacted before they leave the machine. Error messages never contain the credential or text from the remote side.
- If the connection drops after the request was sent, the outcome is unknown; the error says so. For GitHub and Frappe, retrying with the same key is safe; Linear and Jira have no key, so check the tracker first.
- These commands are used by the plan workflow of `ai/planning` (see Phase 36), which asks you to approve the exact plan first. By default the created task names only an opaque Phoenix plan id, never the meeting's title.
