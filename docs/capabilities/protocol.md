# Capability protocol v1

Phoenix capabilities exchange validated [manifest v1](../../protocol/schemas/capability-manifest-v1.schema.json) declarations and [event protocol 1.x](../../protocol/src/event.ts) envelopes with Core. `manifest_version: "1"` and `compatibility: { "protocol": "1" }` are optional for legacy consumers; if present they must equal `"1"`. The current event envelope's `version` is `"1.1"`; it is not the capability package version. Read [migration](migration.md) before changing old manifests.

## Manifest fields

Required: `id`, `name`, `version` (capability SemVer), `description`, SPDX `license`, `events` (exact names or suffix `.*`), `commands` and `permissions`. Optional: `author`, `homepage`, `data_categories`, `healthcheck` interval/timeout, JSON Schema `config_schema`, builtin `secrets`, `state_rules`, `ui_extensions`, `manifest_version`, and `compatibility`. Commands contain `name`, `description`, `side_effect` (`none`, `read`, `write`, `execute`, `external`, `production`), and optional `permissions`, JSON Schema `input_schema`, `timeout_ms`. The schema refuses extra top-level fields and unsupported version literals. Cross-field validation rejects duplicate command names, undeclared command permissions, bad embedded JSON Schemas, state rules outside declared events, and reserved ids/event namespaces (`core`, `pet`, `system`, `security`, `phoenix`, `fawkes`, `capability`, `notification`). `events: []` is valid for command-only capabilities.

Event envelopes have `event_id`, `version`, `timestamp`, `source`, `event_type`, `severity` and `payload`, with optional context such as `correlation_id` and `subject`; prefer [`events` builders](sdk.md) for recognized types. Core binds the `source` to the capability id, rejects event types outside declared patterns, and deduplicates event ids. For custom names, declare their namespace and any `state_rules` you need. `emit` returns a result you should inspect; calling it before enable does not grant permissions. Do not put credentials in event payloads.

## External transport

The SDK manages this contract; other language implementations must implement it themselves. Bind the callback to a loopback endpoint and register using `POST /api/capabilities/register` with `{ manifest, endpoint, callback_secret }` and the Core session token as bearer authorization. Core replies with a distinct capability token. Core sends the callback secret as `X-Phoenix-Capability-Token` to `GET /health`, `POST /phoenix/lifecycle` (`{ action: "enable" | "disable", config? }`), and `POST /commands/{name}` (`{ input, operation_id }`, reply `{ result }`). The external process posts events to `/api/capabilities/{id}/events` with its Core-issued token in the same header. After Core restart, re-register with the fresh session token; the SDK does this on an event 401 and retries that event with the same event id. Sessions and callback tokens are secrets: never log them or expose the loopback server on a public interface.

Commands run through Core's permission gateway, input validation and operation tracking. Reads and none run without per-call confirmation; write/execute/external/production or sensitive permissions await explicit approval. `POST /api/capabilities/{id}/commands/{name}` creates an operation; `GET /api/operations/{id}` exposes its result. On failure, return an error status rather than fabricating success. Health checks report healthy/degraded/unhealthy. For lifecycle and security details see [model](model.md) and [security](security.md); for a real-Core, local-only walkthrough run the [SDK smoke script](sdk.md#executable-examples-and-smoke).
